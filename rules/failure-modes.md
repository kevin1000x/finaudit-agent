# 已发生过的失败模式

**这里只放已经真实犯过的错，不放假想风险。** 每条给出发生次数与识别方法。
新条目只在**实际犯错之后**追加——预防性的告诫属于 `pitfalls.md`。

## 准入条件（2026-08-27 新增，登记册 `L-24`）

上面那句话只划了**一半**边界（「我们犯过的」vs「别人犯过的」）。
另一半是：**我们犯过的错也不是每一条都该进来。**

出处 `references/deepseek-harness-docs-part2.md` HD2-14
（`postmortem/README.md:9`、`:7`）：harness 的 postmortem 有**三条硬判据**，
三条**必须同时成立**——

| 判据 | 含义 | 不满足时该去哪 |
|---|---|---|
| **subtle** | 机制不显然，读代码 / 读文档看不出来 | 显然的错 ⇒ 直接改掉，不立条目 |
| **systemic** | 漏网的原因是**流程或工具的缺口**，`not a one-off typo` | 一次性笔误 ⇒ 改掉就完了 |
| **costly to rediscover** | 下一个人重新踩一遍的代价高 | 重发现成本低 ⇒ 不值一条 |

`postmortem/README.md:7` 还划了另一条界：**postmortem 不是「设计决策记录」。**
对应到本仓：决策去 `DECISIONS.md`，预防性告诫去 `pitfalls.md`，本文件只收**事故**。

**为什么现在补这条**：本文件当时是 F-1…F-8 的扁平清单，**没有准入条件**，
长期必然变成「所有犯过的错都往里堆」——那时它就不再是「值得回头读的八条」，
而是一本流水账，谁也不会在会话开始时扫一遍（`CLAUDE.md` 要求扫的正是这份）。

**它已经在起作用（这不是假设，是本轮实际发生的三次）**：
登记册 `L-21`、`L-68`、`L-23` 三条的「目的地」列原本都写着本文件，
逐条按上表核对后**全部改道 `pitfalls.md`**——它们是**外部项目**犯的错，
本仓无实例，`subtle` 与 `costly` 都成立，**`systemic` 那一栏填不出「我们的哪个流程缺口漏掉了它」**，
因为我们根本没走到那一步。⇒ 准入条件把「凭感觉归档」变成了**逐栏填表**，
填不满的自己就落到 `pitfalls.md` 去了。

⚠️ **本条只约束新增，不追溯。** 现有 F-1…F-8 不重新审一遍——
回头拿新准入条件去删已经记下的事故，等于**用今天的标准修改昨天的记录**，
与 `D-012`「不修改后重用」是同一条原理。

### 满足准入条件、但**刻意不在此立条目**的（2026-08-27 操作者裁决，选项 a）

准入条件（subtle + systemic + costly）**筛出来的东西不自动进本文件**。
下面两条本仓真实实例三栏全部填得出，**依然不在这里立 `F-` 条目**——
`D-009` 要求同一件事只有一个权威落点，落两处以后必然改一处漏一处。
**本节只放指针，不复述内容。**

| 登记册 | 一句话 | 权威落点 |
|---|---|---|
| `L-7` | 引用散文必错，`grep` 得出来的才准 —— ch9 勘误 10 条错误行号里 7 条落在无代码的散文段 | `references/README.md` 硬规则第 5 条 (a) |
| `L-23` | 覆盖 / 完整性检查的**基准集合必须独立于被检查物** —— 本仓实例：第六道门 R5 的基准取自登记册自身 | `rules/pitfalls.md` 第 19 条 |

**为什么不是「准入条件白写了」**：准入条件回答的是「够不够格被记住」，
本节回答的是「**记在哪一份文件里**」。两个问题都得答，
上表那三栏填满只完成了第一问。⇒ 一般形态：
**准入判据决定去留，`D-009` 决定归属；先过判据，再定归属。**

⚠️ 本节**不是**豁免名单，往里加东西不会让任何检查放行。
它存在的唯一理由是：不写下来，下一轮会重新问一次同样的问题。

## F-1 用「代码里没有」断言「实际没有」 —— 2026-08-15 一天内 3 次

| # | 错误断言 | 实况 |
|---|---|---|
| 1 | cninfo 审计意见零命中，需加数据源 | 年报 PDF 里本来就有，缺的是抽取器 |
| 2 | cninfo 只有 roa/ocf 两个字段 | 那是 AKShare 路径的窄化选择，不是能力上限 |
| 3 | cninfo 没用 HuggingFace（全仓 grep 无匹配） | **后端跑在哪仓库里根本不写**，在 Pages secret 里 |

三次都是 grep 几行就下结论。

**识别方法**：任何形如「X 没有 Y」的断言，先问**「我查的范围能不能覆盖 Y 可能存在的位置」**。
部署配置、密钥、运行时环境、数据内容——这四类**天然不在代码仓库里**。

**硬规则**：不对操作者的系统下「没有 X」的判断。可以说「我在仓库里没搜到 X」。

## F-2 给 flag 编造求不出值的 trigger —— 2026-08-15 3 次

`unit_scale_mismatch ← 营业收入为零`、`parent_only_scope ← 流动资产为负`、
`basis_version_mismatch ← standard_basis.version != ...`（`standard_basis` 是列表，标量引用无解）。

共同点：**报表里没有承载该概念的字段，于是拿手边能求值的东西凑一个。**
凑出来的是**永远不会正确触发的假规则**——与 POC-01 发现的「`common_pitfalls` 是散文」同型，
只是换到了 trigger 上。

**硬规则**：只有当**存在真实字段能诚实触发**时才声明 flag。
没有字段就不声明，把风险如实标 `advisory_only` 并注明「本定义无法对此设可求值规则」。

**执行机制（2026-08-24 补，落地待办 L-4）**：本条此前**只有识别方法，没有执行机制**
——而「规则写出来了不等于它会触发」正是本条自己讲的毛病。
`scripts/check_gates.py`（第六道门）是它的机器化：机械拒绝**非空但没有任何可失败点**
的测试，以及**恒真断言**（`assert True` / `assert x == x`）。
外部依据是 harness 的 `invariants.md:59`（逐字：拒绝「非空但省略/忽略 reporter 的检查」）
与 `:5`（禁止断言「service/method 存在」这类恒真物）。

**它只覆盖了「测试侧」。** flag 的 trigger 侧（本条的原始形态）**仍无门禁**——
判断一个 trigger 能否被真实字段求值，要到 Phase 1.5 接上抽取器输出才验得了。
不许把「第六道门通过」读成「F-2 已经不会再犯」。

## F-3 如实标注读得少 ≠ 读过 —— 2026-08-15

建了 `references/` 并定下「每条标注读到什么程度」的规则，然后**第一版三份里有两份
是照着工具生成的摘要写的**，如实标了「只读了 1/16 章」就当交差。

**标注是为了防止越界断言，不是用来替代阅读的。**

**硬规则**：被要求「研读」时，读原文。上下文不够就**开 subagent 用独立上下文读**，
不要自己挑切片然后标注「只读了一部分」。

## F-4 记进台账 ≠ 做了 —— 2026-08-15

为解决「聊着聊着就完了」建了 `docs/agent/OPEN-ITEMS.md`，
然后把「ROADMAP 改写」记进 N-2 的判据栏**就没管了**，直到操作者问「roadmap 更改了吗」。

**硬规则**：台账里的「判据」是**待办**不是**已办**。
每次会话结束前扫一遍 A 区（阻塞中）与 N 区（新增），把能做的做掉。

## F-5 规格只跟实现对齐，没跟下游消费者对齐 —— 2026-08-15

01-02 把 R4 的命名空间白名单与 R8 的 `enforced_by` 类别集**照抄自实现**，
反向核对也只比对「规格 ↔ 实现」，17 条断言全过就 apply 了。
结果两个集合都少一项（`kpi`、`derivation`），wave 3 开写第一批定义时才炸出来。

规格是给**尚未写出的东西**用的。只跟已有实现对齐，等于只验证了
「规格描述了现在有什么」，没验证「够不够写出接下来要写的东西」。

**硬规则**：任何锁定枚举集的变更，反向核对必须**同时比对下游计划里已写明要用的取值**。

## F-9 拿「已经存在的东西」当「现在做得到」的证据 —— 2026-09-07

想在 Hugging Face 建一个 docker Space。实测了两格：
`private + static` 可以、`private + docker` 402（要 PRO）。
**另外两格没测，是推出来的** —— 依据是「`RGT07/cninfo-financial-analyzer`
是 public + docker，在同一个免费账号上正跑着，昨天还推过内容」。
于是我下了结论：卡住的是 private，公开就免费。

据此写了一份 `D-005` 修订、改了 `Dockerfile` 与部署 README、跑完七道门禁、**提交了**。
然后真去建 —— **public + docker 同样 402**。补完矩阵：
**卡住的是 docker，与可见性完全无关。公开换不来任何东西。**

那份修订的核心论证（「三者不能同时成立，放弃其中一项」）是**一笔不存在的交易**。

**这次错的形状**：一个已经存在的产物，证明的是「**曾经**可以这样造」，
不是「**现在**可以这样造」。平台策略、免费额度、配额、API 权限都会随时间收紧，
而既有资源通常被祖父条款豁免 —— **它们恰恰是最不能代表当前策略的样本。**

**它与 `F-1` 的区别**：`F-1` 说的是「不对操作者的系统下『没有 X』的判断」，
方向是**否定**；这一条方向是**肯定** —— 「别人那儿有 X，所以我也能有 X」。
两条是同一件事的两面：**都是拿手边一个观察去替代一次本可以直接做的测量。**

**识别方法**：正要写「⇒ 所以 A 也可以」的时候问一句 ——
**「这一格我测过吗，还是我从旁边那格推的？」**
矩阵型的问题（可见性 × 类型、账号 × 权限、版本 × 平台）尤其危险，
因为推断读起来和测量一模一样。

**硬规则**：能直接测的事，不许推断。
外部服务的**创建/配额/计费**类问题一律实测所有相关组合再下结论；
测不了的格子标 `UNVERIFIED`，**不许用同类产物的存在去填**。
在这类结论上写决策文档之前，先把矩阵跑完 —— 否则会像这次一样：
七道门禁全绿、提交也干净，而**被门禁保护的那个论证是空的**。

## F-8 跑了门禁但没让它挡住后面的动作 —— 2026-08-16 两次

| # | 命令形态 | 后果 |
|---|---|---|
| 1 | `pytest -q \| tail -3 && git commit` | 管道把 pytest 的非零退出码吞掉，**带着一个红测试提交**（`58adfb5`） |
| 2 | `scan; git commit` | 分号不短路，**扫描已经红了照样提交**（`a8cc782`） |

两次都不是忘记跑门禁——**门禁跑了，输出也打出来了，我甚至在回复里读了它**，
但它在 shell 层面没有拦住后面的 `git commit`。

**这与 F-2「规则写出来了不等于它会触发」是同一个物种**，只是换到了我自己的命令行上。
也与本项目从三个外部项目收集到的那条模式同型：
**自证机制说通过了，但它证明的不是它声称证明的事。**

**识别方法**：任何「先验证、后提交」的命令，问一句
**「如果验证失败，后面那条命令还会不会执行？」** 答案必须是「不会」。

**硬规则**：验证与提交**一律用 `&&` 串联**，让退出码物理成门。
禁止用 `;` 串联，禁止在门禁命令后接管道（`| tail` / `| head`）——
要看尾部输出就先重定向到文件、再单独 `tail`，把退出码留给 `&&`。

## F-7 有 subagent 在跑时宣告任务完成 —— 2026-08-15

**硬规则**：有背景 agent 未返回时，不写收尾总结、不说「做完了」。
如实说哪几个还在跑。它们的结论回来之前，**不预测、不代写、不假设**。
