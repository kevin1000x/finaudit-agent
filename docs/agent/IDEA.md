# IDEA — 问题陈述

> 本文件回答"我们在解决什么问题"，不回答"我们要实现什么方案"。

## Problem

财务与审计场景里，AI 给出的分析结论没人敢直接用。

关键不在于 AI 更容易算错——人也会算错。关键在于**错了查不出来在哪一步错**。一个审计师拿到人做的底稿，可以顺着取数、口径、计算逐层复核；拿到 AI 的回答，只能看到一个数字和一段听起来很有道理的解释。

## Target user

第一用户是**我自己**：一个有审计与税务实习背景、正在做商业分析、需要反复核对财务口径的人。

第二圈层（假设，未验证）：财务 BP、经营分析、审计助理——需要频繁取数并对数字负责的人。

⚠️ 这一条是**假设**，不是事实。目前没有任何第二圈层用户访谈证据。不要把它当需求依据。

## Current workflow

现在的做法是：人打开年报 PDF，人找到指标，人确认口径是不是同一个，人算，人再核一遍。中间任何一步用 AI 加速，都会引入一个"这个数到底靠不靠谱"的新问题，而复核成本往往比自己算还高。

## Pain

三个具体的痛点，都来自真实经历：

1. **口径不一致**。"净利润"在不同语境下可能是净利润、归母净利润、扣非归母净利润。人对着说也经常说岔，让 AI 猜必然出错，而且它会自信地给出一个数字。
2. **无法逐层复核**。AI 的自然语言解释是事后编的，不是执行过程的真实记录。看解释复核等于看小说验账。
3. **失败无法归因**。答案错了，不知道是没找到该找的资料、还是用错了指标定义、还是算错了、还是格式不对。四种错误的修法完全不同。

## Desired outcome

一次问答的输出不是一个数字，而是一个**可复核的包**：

```text
答案 + 用了哪张表 + 哪个指标口径（含版本）+ 依据哪条准则
     + 检索命中了什么 + 执行了什么 + 结果哈希 + 耗时与成本
```

判定标准很朴素：**一位有审计背景的人，只看这个包、不看 AI 的解释，能在 5 分钟内独立判断它对不对。**

## Constraints

- 单人开发，每周 ≤ 8 小时，且转正优先（D-008）
- 只能用公开数据，任何雇主/客户数据一律禁止（D-010）
- 不训练、不微调（D-011）
- 主仓暂不开源（D-005）
- 已有可复用资产：`cninfo-financial-analyzer`（年报下载、PDF 解析、情感词典、Fog、TNI）

## Explicit non-goals

- 不做通用 Data Agent / ChatBI / 多数据源
- 不做企业数据治理与权限系统
- 不做 SaaS / 多租户
- 不为了展示而建知识图谱

## Key assumptions

| # | 假设 | 已验证？ |
|---|---|---|
| A1 | 财务指标口径**能够**被固化成无歧义的机器可读定义 | ❌ 未验证 —— 这是最危险的假设 |
| A2 | 证据链能让人在 5 分钟内独立复核 | ❌ 未验证 |
| A3 | 存在纯向量 RAG 答不了而图能答的财务问题 | ❌ 未验证，且**允许证伪后跳过** |
| A4 | 垂直领域的口径优势通用 Agent 无法覆盖 | ⚠️ 部分证据（竞品都在做通用语义层，但没有绑准则依据） |
| A5 | 第二圈层用户存在且有同样痛点 | ❌ 完全无证据，纯推测 |

## Critical unknowns

- **U1**：一个财务指标的口径，到底能不能写成一份让两个专业人士看完不产生分歧的定义？如果不能，H1 就不成立。
- **U2**：证据链需要哪些字段才够复核？多了是噪音，少了不够用。目前没有依据，不许提前拍板（D-U-01）。
- **U3**：会计准则的可用公开语料从哪来、是否允许再分发？

## Success definition

**不是**"做出一个能用的产品"。是：

> 在 2027 年 3 月前，对 H1 / H2 / H3 三个假设各得到一个**有证据支持的结论**——通过或不通过都算成功；**只有"做了很多东西但说不清证明了什么"才算失败。**

## 对这个想法本身的质疑（Devil's advocate，DISCOVER 阶段自检）

诚实记录几条对本项目不利的判断，它们没有被回答，只是被接受了：

1. **这个问题可能不需要软件解决。** 口径不一致的根因是组织没有统一口径字典，而不是没有工具。一份 Excel 口径表 + 团队共识可能解决 80%。
   → 接受。本项目的差异在于口径定义要被**机器消费**并驱动拒答，而不是给人看。但这个差异是否值 4 个月，未证。

2. **第二圈层用户可能不存在。** A5 完全没有证据。项目实际上是"给我自己做的工具"，这没问题，但不该假装它有市场。
   → 接受。对外叙述时按"个人工具 + 方法验证"定位，不吹市场。

3. **最省事的替代方案是不做。** 直接用现成的 `datafoundry` 或 `text-to-sql-agent-system`，把时间投在 SQL 与商分硬技能上，对秋招的边际收益可能更高。
   → 部分接受。因此 Phase 0（cninfo 实证结论）被排在最前——它 4 小时/周、两三周出结果，是整条路线上性价比最高的一段。若 Phase 0 之后精力不足，**在 Phase 1 结束时停下也是一个完整的故事**。

4. **"证据链"可能是伪需求。** 也许人根本不会花 5 分钟复核，宁可直接自己算。
   → 这正是 H2 要测的。若复核一致率 < 60%，按 `EVAL_CASES.md` §8 停止并回到架构阶段。
