> 模式：`POC`　｜　状态：**POC-01 已执行（2026-08-10，判定 PASS）**　｜　POC-02 未执行
> 目的不是证明项目能做，而是**尽快杀死错误假设**。优化的是单位工程量的信息增益，不是代码量。

## POC-01 — 口径可判定性（H1）

### Hypothesis

> 一份财务指标的口径定义，能够写到让**两个有财务背景的人独立阅读后，对同一道题给出相同的取数与计算路径**，且分歧可以被机械检出。

### 为什么这是最危险的假设

它是唯一一个"若不成立则整个方向作废"的假设：

- 若口径无法无歧义定义 → 语义层（L1）没有意义 → Hook 无从校验（L3）→ 证据链里最关键的一项失去内容 → 整个项目退化成又一个 NL2SQL 包装。
- 相比之下，H2（证据链可复核）失败只需退回 Option A；H3（图谱必要性）失败根本不算失败。

同时它也是**最便宜可测**的：不需要写 Agent、不需要 RAG、不需要 TUI，只需要三份 YAML 和两个人。

### 最小实验

**预算：2 小时。超时即停，按已有结果判定。**

1. **选 3 个指标**，必须覆盖三种不同的歧义来源：
   - `net_profit_attributable_excl_nonrecurring`（扣非归母净利润）—— **口径层级歧义**（净利润 / 归母 / 扣非三层）
   - `operating_cash_flow_ratio`（经营现金流量比率）—— **分母歧义**（流动负债 vs 总负债）+ **零分母**
   - `revenue_growth_yoy`（营业收入同比增长率）—— **时段歧义**（缺失期、追溯调整、并表口径变更）

2. **为每个指标写口径定义**，按 `PROJECT_SPEC.md` §5.1 的字段：`source_fields` / `formula` / `standard_basis` / `period_semantics` / ≥3 条 `common_pitfalls`。

3. **写 5 道测试题**，每道题使用**日常说法**而非规范名称（例如问"净利润"而不是"扣非归母净利润"），其中至少 1 道题的指标**故意不在定义集内**（测拒答）。

4. **独立回答**：找一位有财务背景的人（或用两个独立的 LLM 会话，各自只看定义不看对方），仅凭口径定义独立给出取数路径与计算式。

5. **机械比对**：两份回答的 `source_fields` 集合、`formula` 结构、`period_semantics` 是否一致。

### 输入

- 3 份口径定义 YAML
- 5 道自然语言问题（冻结后再给回答者）
- `cninfo` 已有的年报数据字段清单（不需要真的取数，只需要指出取哪些字段）

### 可观测输出

| 观测项 | 记录方式 |
|---|---|
| 两份回答的字段集合一致性 | 完全一致 / 部分一致 / 不一致 |
| 公式结构一致性 | 同上 |
| 未定义指标的处理 | 拒答 / 猜测 |
| 定义中被指出的缺陷 | 自由文本，逐条记录 |

### 判定阈值

```text
PASS          5 道题中 ≥ 4 道两份回答完全一致，且未定义指标被正确拒答
              → H1 有初步支持，按计划进入 Phase 1

FAIL          ≥ 3 道题出现实质性分歧（取数字段或公式结构不同）
              → H1 不成立。停止本方向，退回 Option D（不自建）

INCONCLUSIVE  介于两者之间，或分歧集中在定义可以补写的细节
              → 补写定义后重测一次。仅允许重测一次；第二次仍不达标按 FAIL 处理
```

### Kill criterion

**FAIL 即停止整个项目方向**，不做"那我再改改定义"的循环。定义可以无限细化到消除分歧，但那时它已经不是"口径定义"而是"答案"，H1 就在实质上被证伪了。

这条规则的意义是防止最常见的自欺：把实验一直调到通过为止。

### 明确不做

- ❌ 不写 Agent、不接 LLM API 做编排
- ❌ 不做 RAG、不建图
- ❌ 不写 TUI
- ❌ 不真的去取数计算（只验证"取哪些字段、怎么算"是否一致）
- ❌ 不为这个实验建任何抽象、框架或目录结构

### 三个分支

| 结果 | 学到了什么 | 接下来做什么 |
|---|---|---|
| **PASS** | 口径可以被写成机器可读且人可复现的定义 | Phase 1 全量做 20 个指标；把这 3 个作为模板 |
| **FAIL** | 财务口径的分歧源于业务实质判断，不是定义缺失 | 停止本方向。`cninfo` 仍按 Phase 0 补实证结论，作为独立项目 |
| **INCONCLUSIVE** | 定义字段设计不足 | 按暴露的缺陷补 1–2 个字段后重测一次，仅此一次 |

## POC-02 — 图谱必要性（H3）· 延后至 Phase 3 前

不在当前执行范围。前置条件：Phase 2 的 H2 判定门通过。

**Hypothesis**：存在纯向量 RAG 答不了而知识图谱能答的财务问题。
**判定**：必须在真实年报语料中找到 ≥ 3 个可举实例的问题，并**实证**（不是论证）纯 RAG 答不了。
**Kill criterion**：找不到 → **不建图谱**。这不是失败，是省下的工作量（D-007）。
