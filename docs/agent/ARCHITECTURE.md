---

## 1. 关键架构决策

只有三个决策真正影响后续所有工作：

- **AD-01**：做通用还是垂直？
- **AD-02**：先做 Agent 编排还是先做语义层？
- **AD-03**：证据链是产品的一部分还是可观测性的一部分？

其余（用哪个 LLM SDK、TUI 用 Textual 还是 Rich、向量库选谁）都是可逆的实现细节，不在本文件决策。

---

## 2. 方案

### Option A — 最简：只做语义层，不做 Agent

**架构**：一组 YAML 口径定义 + 一个校验器 + 一个查询 CLI。人问、人查、机器只保证口径一致。

| 维度 | 评价 |
|---|---|
| 实现复杂度 | 极低（2–3 周） |
| 运维复杂度 | 无 |
| 失败模式 | 没人用（包括我自己）；变成一堆静态 YAML |
| 安全含义 | 无执行，无风险 |
| 可逆性 | 完全可逆，是其他所有方案的子集 |
| 依赖的假设 | 只依赖 H1 |
| 测试策略 | 单元测试 + 口径歧义评测 |

**为什么可能成功**：H1 是地基，先验证地基是最省事的路径。且这一层单独就能写进简历。
**为什么可能失败**：没有消费方，无法验证口径定义是否真的够用；"够用"只能靠 Agent 实际去用才知道。

### Option B — 平衡：语义层 + 可信执行层 + TUI（**推荐**）

**架构**：L0 数据层（cninfo 已有）→ L1 语义层 → L3 可信执行层（Hook + Trace + Eval）→ L4 TUI。**L2 知识层（RAG/图谱）延后到 Phase 3，且图谱条件性建设。**

| 维度 | 评价 |
|---|---|
| 实现复杂度 | 中（Phase 1–2，约 3 个月，8h/周） |
| 运维复杂度 | 低（本地运行，无服务） |
| 失败模式 | 证据链设计错 → 复核一致率不达标（H2 门会抓住这个） |
| 安全含义 | 有代码执行 → 需要 AST 静态校验；不是沙箱，只用公开数据 |
| 可逆性 | 高：L1 可独立留存，L3/L4 可丢弃 |
| 依赖的假设 | H1 + H2（H3 可选） |
| 测试策略 | 分层评测 + 复核实验 |

**为什么可能成功**：每一层单独可讲；差异化点（口径 + 证据链）恰好落在竞品的空隙上；工作量与 8h/周 预算匹配。
**为什么可能失败**：H2 不成立时，做完的 L3/L4 大部分白费；且"垂直 + 证据链"这个空隙可能是没价值才空着。

### Option C — 可扩展：完整四层 + 图谱 + 多数据源

**架构**：Option B 全量 + 知识图谱 + 抽象出数据源适配层。

| 维度 | 评价 |
|---|---|
| 实现复杂度 | 高（6 个月+） |
| 运维复杂度 | 中（图数据库） |
| 失败模式 | 直接对上 `datafoundry`（648★，团队维护），功能上必输；面试答不出差异化 |
| 可逆性 | 低，抽象层一旦建立难以拆除 |
| 依赖的假设 | H1 + H2 + H3 全部成立 |

**为什么可能失败**：**在 H3 未验证前就为图谱建基础设施，违反"先验证最危险的假设，再搭基础设施"**。多数据源适配层是典型的无当前消费者的抽象。

### Option D — 不自建：直接用现成方案

**架构**：部署 `datafoundry` 或 `text-to-sql-agent-system`，把省下的时间投到 SQL 与商分硬技能上。

| 维度 | 评价 |
|---|---|
| 实现复杂度 | 极低 |
| 对秋招的短期收益 | **可能最高**——SQL 与 AB 实验是商分面试的确定性得分点 |
| 失败模式 | 没有可讲的原创项目；面试问"你自己做过什么"时只能说"我用过某个开源工具" |
| 可逆性 | 完全可逆 |

**为什么可能成功**：这是**最诚实的替代方案**。若时间紧张，它的期望收益可能高于半成品项目。
**为什么可能失败**：AI PM 方向必须有自己的项目；且用现成工具无法回答"你怎么保证口径对"这个问题——现成工具恰恰不解决它。

## 3. 对比

| 维度 | A 只做语义层 | **B 语义层+执行层+TUI** | C 完整四层 | D 不自建 |
|---|---|---|---|---|
| 工作量 | 2–3 周 | 3 个月 | 6 个月+ | 0 |
| 依赖假设数 | 1 | 2 | 3 | 0 |
| 与竞品正面冲突 | 无 | 弱 | **强** | 完全重合 |
| 每阶段可独立讲 | 是 | 是 | 否 | 否 |
| 失败时的沉没成本 | 极低 | 中（L1 保留） | 高 | 无 |
| 对三个投递方向的覆盖 | 商分/财务 | **三个都覆盖** | 三个都覆盖 | 无 |
| 8h/周 预算下可行性 | 高 | **中高** | 低 | — |

## 4. 决策

**选 Option B。** 对应决策记录 D-001（垂直）、D-002（语义层先行）、D-003（证据链一等）、D-007（图谱条件性）。

三个关键决策的答案：

- **AD-01 → 垂直。** 通用方向已被 648★ 项目占位，个人项目无法竞争，且面试无法回答差异化问题。
- **AD-02 → 语义层先行。** 它是唯一别人抄不走的一层，且不依赖后续阶段就能独立成立（抗风险）。
- **AD-03 → 证据链是产品的一部分。** 给不出证据链判为失败，不判为"降级成功"。这是与所有竞品的分界线。

### 为什么其他方案输了

- **A 输在**：没有消费方就无法验证口径定义是否够用。B 包含 A，且多了验证手段。
- **C 输在**：在 H3 未验证前建图谱基础设施，违反"先验证最危险假设"。B 把图谱留在 Phase 3 且设了前置检验，C 提供的额外价值全部依赖未验证假设。
- **D 输在**：现成工具不解决口径问题（这正是我要解决的），且 AI PM 方向必须有自己的项目。**但 D 保留为退路**——见下方风险处置。

### 什么证据会推翻这个决策

| 证据 | 动作 |
|---|---|
| POC-01 显示口径无法无歧义定义（H1 不成立） | 整个方向作废，退回 Option D |
| 复核一致率 < 60%（H2 不成立） | 退回 Option A，只保留语义层 |
| 出现开源项目已把"财务垂直 + 准则绑定 + 证据链"做完 | 退回 Option D，转为使用并贡献 |
| 连续两周未推进 | 砍到 Option A 的范围 |

## 5. 可逆性

| 决策 | 可逆性 | 说明 |
|---|---|---|
| 垂直而非通用 | **高** | 语义层可以后加数据源，反向（从通用收窄）才难 |
| 语义层先行 | **高** | 顺序问题，随时可调 |
| 证据链一等 | **中** | 字段集固化后改动成本上升，因此 U-01 明确不提前拍板 |
| 不建图谱（默认） | **高** | 不建的成本是零，建了再拆才贵 |
| 暂不开源 | **高** | 随时可开，开了不可撤 |

## 6. Devil's advocate（独立质疑，未被回答的部分）

以下质疑**没有被驳倒**，只是被接受为已知风险：

1. **"口径可判定"可能本身就是伪命题。** 财务口径的分歧常常来自业务实质判断，不是定义缺失。把它写进 YAML 可能只是把分歧从口头搬到文件里。
   → 未回答。这正是 POC-01 要测的。**如果 POC-01 失败，本项目应当停止而不是调整。**

2. **证据链的复核成本可能高于重算成本。** 对一个熟练的财务人，自己算一遍可能比读 8 个字段的证据链更快。
   → 未回答。H2 实验会给出答案，但即使一致率达标，也不等于人愿意用。

3. **这个项目的真实目的是求职，不是解决问题。** 那么最优解可能是做一个更容易讲的项目，而不是更正确的项目。
   → 部分接受。缓解方式是"每阶段都是完整故事"（ROADMAP 的设计），使得任何时点停下都可讲。

4. **三套方法论（GSD + Superpowers + OpenSpec）叠加，流程可能压过项目本身。**
   → 接受。D-009 设了减法触发条件：任一阶段流程开销 > 产出时间 30% 就删掉贡献最小的一套。

## 7. 需要 POC 验证的假设

**H1（口径可判定性）。** 它是唯一一个"若不成立则整个方向作废"的假设，因此必须最先验证。实验设计见 `POC.md`。

H2 的验证需要先有证据链实现，无法前置，安排在 Phase 2 门。
H3 的验证是证伪导向的，安排在 Phase 3 前置检验。
