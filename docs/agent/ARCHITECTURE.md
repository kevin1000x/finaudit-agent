## 2. 方案

### Option A — 最简：只做语义层，不做 Agent

**架构**：一组 YAML 口径定义 + 一个校验器 + 一个查询 CLI。人问、人查、机器只保证口径一致。

| 维度 | 评价 |
|---|---|
| 实现复杂度 | 极低（2–3 周） |
| 运维复杂度 | 无 |
| 失败模式 | 没人用（包括我自己）；变成一堆静态 YAML |
| 安全含义 | 无执行，无风险 |
| 可逆性 | 完全可逆，是其他所有方案的子集 |
| 依赖的假设 | 只依赖 H1 |
| 测试策略 | 单元测试 + 口径歧义评测 |

**为什么可能成功**：H1 是地基，先验证地基是最省事的路径。且这一层**单独就是一个完整产物** —— 不依赖上层 Agent 就能用、能验。
**为什么可能失败**：没有消费方，无法验证口径定义是否真的够用；"够用"只能靠 Agent 实际去用才知道。

### Option B — 平衡：语义层 + 可信执行层 + TUI（**推荐**）

**架构**：L0 数据层（cninfo 已有）→ L1 语义层 → L3 可信执行层（Hook + Trace + Eval）→ L4 TUI。**L2 知识层（RAG/图谱）延后到 Phase 3，且图谱条件性建设。**

| 维度 | 评价 |
|---|---|
| 实现复杂度 | 中（Phase 1–2，约 3 个月，8h/周） |
| 运维复杂度 | 低（本地运行，无服务） |
| 失败模式 | 证据链设计错 → 复核一致率不达标（H2 门会抓住这个） |
| 安全含义 | 有代码执行 → 需要 AST 静态校验；不是沙箱，只用公开数据 |
| 可逆性 | 高：L1 可独立留存，L3/L4 可丢弃 |
| 依赖的假设 | H1 + H2（H3 可选） |
| 测试策略 | 分层评测 + 复核实验 |

**为什么可能成功**：每一层单独可讲；差异化点（口径 + 证据链）恰好落在竞品的空隙上；工作量与 8h/周 预算匹配。
**为什么可能失败**：H2 不成立时，做完的 L3/L4 大部分白费；且"垂直 + 证据链"这个空隙可能是没价值才空着。

### Option C — 可扩展：完整四层 + 图谱 + 多数据源

**架构**：Option B 全量 + 知识图谱 + 抽象出数据源适配层。

| 维度 | 评价 |
|---|---|
| 实现复杂度 | 高（6 个月+） |
| 运维复杂度 | 中（图数据库） |
| 失败模式 | 直接对上 `datafoundry`（648★，团队维护），功能上必输，且说不出差异化在哪 |
| 可逆性 | 低，抽象层一旦建立难以拆除 |
| 依赖的假设 | H1 + H2 + H3 全部成立 |

**为什么可能失败**：**在 H3 未验证前就为图谱建基础设施，违反"先验证最危险的假设，再搭基础设施"**。多数据源适配层是典型的无当前消费者的抽象。

### Option D — 不自建：直接用现成方案

**架构**：部署 `datafoundry` 或 `text-to-sql-agent-system`，把省下的时间投到 SQL 与商分硬技能上。

| 维度 | 评价 |
|---|---|
| 实现复杂度 | 极低 |
| 短期产出速度 | **可能最快** —— 现成工具，几乎不用自己写 |
| 失败模式 | 没有任何原创产物 —— 能说的只有「我用过某个开源工具」 |
| 可逆性 | 完全可逆 |

**为什么可能成功**：这是**最诚实的替代方案**。若时间紧张，它的期望收益可能高于半成品项目。
**为什么可能失败**：AI PM 方向必须有自己的项目；且用现成工具无法回答"你怎么保证口径对"这个问题——现成工具恰恰不解决它。

## 4. 决策

**选 Option B。** 对应决策记录 D-001（垂直）、D-002（语义层先行）、D-003（证据链一等）、D-007（图谱条件性）。

三个关键决策的答案：

- **AD-01 → 垂直。** 通用方向已被 648★ 的团队项目占位，单人项目在功能面上无法竞争，也说不出差异化在哪。
- **AD-02 → 语义层先行。** 它是唯一别人抄不走的一层，且不依赖后续阶段就能独立成立（抗风险）。
- **AD-03 → 证据链是产品的一部分。** 给不出证据链判为失败，不判为"降级成功"。这是与所有竞品的分界线。

### 为什么其他方案输了

- **A 输在**：没有消费方就无法验证口径定义是否够用。B 包含 A，且多了验证手段。
- **C 输在**：在 H3 未验证前建图谱基础设施，违反"先验证最危险假设"。B 把图谱留在 Phase 3 且设了前置检验，C 提供的额外价值全部依赖未验证假设。
- **D 输在**：现成工具不解决口径问题（这正是我要解决的），且 AI PM 方向必须有自己的项目。**但 D 保留为退路**——见下方风险处置。

### 什么证据会推翻这个决策

| 证据 | 动作 |
|---|---|
| POC-01 显示口径无法无歧义定义（H1 不成立） | 整个方向作废，退回 Option D |
| 复核一致率 < 60%（H2 不成立） | 退回 Option A，只保留语义层 |
| 出现开源项目已把"财务垂直 + 准则绑定 + 证据链"做完 | 退回 Option D，转为使用并贡献 |
| 连续两周未推进 | 砍到 Option A 的范围 |

## 6. Devil's advocate（独立质疑，未被回答的部分）

以下质疑**没有被驳倒**，只是被接受为已知风险：

1. **"口径可判定"可能本身就是伪命题。** 财务口径的分歧常常来自业务实质判断，不是定义缺失。把它写进 YAML 可能只是把分歧从口头搬到文件里。
   → 未回答。这正是 POC-01 要测的。**如果 POC-01 失败，本项目应当停止而不是调整。**

2. **证据链的复核成本可能高于重算成本。** 对一个熟练的财务人，自己算一遍可能比读 8 个字段的证据链更快。
   → 未回答。H2 实验会给出答案，但即使一致率达标，也不等于人愿意用。

3. **这个项目的驱动力是「做出一个能展示的东西」，不纯是「解决一个问题」。**
   那么最优解可能是做一个**更容易讲**的项目，而不是一个更正确的项目。
   → 部分接受。缓解方式是"每阶段都是完整故事"（ROADMAP 的设计），使得任何时点停下都完整。

4. **三套方法论（GSD + Superpowers + OpenSpec）叠加，流程可能压过项目本身。**
   → 接受。D-009 设了减法触发条件：任一阶段流程开销 > 产出时间 30% 就删掉贡献最小的一套。
   → **2026-09-11 兑现**：OpenSpec 27 天零使用，按该触发条件删掉（`D-042`）。
     这条质疑当初是对的。

## 8. Phase 2 闸门的形状（2026-08-22 落地；结论为源码级，非推断）

> **为什么现在写进来**：这条结论 2026-08-19 就已由 deepseek-harness 源码证实，
> 但此前只存在于台账与 handoff 里，**权威文档零命中**。
> 读了不落地等于没读——本节是补这个。
> 出处：`references/deepseek-harness-deep-read-part*.md`（harness @ `47f9438`）。

### 8.1 决策：闸门放进**调用签名**，不放进事件顺序

```text
resolve_scope(...) -> ScopeSpec | Refusal
```

**不采用**「waterfall / 事件优先级」式闸门，**也不采用**「把闸门做成一个可选工具」。

**四条源码级理由**（每条都是读 `vendor/cordis` 读出来的事实，不是设计偏好）：

1. `Plugin.Base` 恰好五个字段，**无 `priority` / `order` / `guard`**；
   `EventOptions` 恰好两个字段。**框架层面就没有「保证跑在最前面」这回事。**
2. `inject` 的依赖一变就卸载重跑 ⇒ **闸门在链条中的位置会漂移**。
3. **`ctx.isolate()` 能在子树里把服务整个换掉，父作用域完全无感** ——
   这条最狠：连**被守卫的对象本身**都能被替换掉，守卫再靠前也没用。
4. `Context.filter` 每次派发都查，闸门若忘写 `global`，**会静默地根本收不到事件**。

⇒ 只要闸门是「链条上的一环」，它就可被绕过、可被漂移、可被静默失效。
**放进调用签名后，绕过闸门在类型上不可表达**，不再依赖运行时纪律。

#### 8.1.1 校正：签名闭合只是**第一道锁**，载荷必须冻结（2026-08-23 补，落地待办 L-3）

上面那句「放进调用签名后绕过在类型上不可表达」**说少了**。
harness 对「参数不可改写」实际上了**四道锁**（`tools.md:385-389` / `:283-290` /
`:299-308` / `:315-324`，见 `references/deepseek-harness-docs-part2.md` §13 Q2）：

| # | 锁 | 挡住什么 |
|---|---|---|
| 1 | **决策联合不携带 args** | 闸门无法「顺手改一下参数再放行」 |
| 2 | **参数跨 lossless-JSON 边界后 deep-freeze** | 拿到引用也改不动 |
| 3 | `Omit<ToolExecution,'signal'> & {signal}` —— **用类型运算精确只解冻一个字段** | 需要可变的那一个字段单独开口，其余仍冻 |
| 4 | **守卫入参声明为 `Readonly`** | 守卫自己也不能改 |

**为什么第 1 道不够**：签名里不带 args，只保证**闸门这个函数**改不了参数；
**若被传进签名的对象本身可写，签名就是装饰**——任何拿到同一引用的人都能改，
而 `tool/call` 在执行前就已入日志、已上屏，此刻改写必然导致四方分叉。
harness 给的理由是**时序论证**，不是道德论证。

**落到本项目**：`resolve_scope(...) -> ScopeSpec | Refusal` 的入参
（口径 id、字段值、批次元数据）**必须在跨入语义层边界时冻结**，
不能只靠「我们不会去改它」。Python 侧的对应物是
`@dataclass(frozen=True)` + 容器传 `tuple` / `Mapping` 而非 `list` / `dict`，
需要可变的字段单独开口并写明为什么。

⚠️ **这条尚未有测试强制**，属设计约束而非既成事实。判据见 `LANDING-BACKLOG` L-3。

#### 8.1.2 扩展点只认抽象方法与封闭类型，不认 docstring（2026-08-26 补，落地待办 L-64）

§8.1 讲的是**闸门**不能靠纪律，本小节是同一条原理在**扩展点**上的应用。

**实证**（`references/hello-agents-framework-core.md` FC-A2，该文 §2.4 / §3.5）：
hello-agents 全仓**只有一个真 ABC**（`BaseLLMAdapter`）；另外三个「期望被覆盖」的方法
（`arun` / `arun_stream` / `_generate_smart_summary`）靠 docstring 声明「需要子类实现」，
而基类给了完整实现——**覆盖与否无任何检查，实测无人覆盖**，
后果直接落在 `core/agent.py:452` 那条静默降级上。

⇒ **本项目凡是「必须由下游提供」的东西，一律用抽象方法或封闭类型表达**，
不用「基类给个默认实现 + docstring 说你该覆盖」。
这与 §8.1 第 4 条（闸门忘写 `global` 就静默收不到事件）是同一个物种：
**能靠纪律绕过的约束，等于没有约束。**

落到本项目的具体接缝：抽取器向语义层提供口径的那一侧、抽取记录的 `kind` 判定方，
若要留扩展点，用 `abc.ABC` + `@abstractmethod` 或封闭枚举 / 显式注册表，
**不用「子类可以覆盖这个方法」的注释**。

#### 8.1.3 工具集定稿前的 MVTS 自检（2026-08-26 补，落地待办 L-76）

`references/hello-agents-ch09-context.md` C9-A9（`ch9:71`）给了一条可直接执行的自检：
**最小可行工具集（MVTS）——如果人类工程师都说不准该用哪个工具，别指望智能体做得更好。**

⇒ **Phase 2 工具集定稿前跑一次这个自检**：把候选工具清单交给一个没参与设计的人，
给三个真实问题，让他说出每题该调哪几个工具。**说不准的那两个必须合并或删掉一个。**
它要的不是「工具更少」，是**工具边界可判定**——
与 §8.2「`Refusal` 必须是封闭枚举」同源：边界不可判定时下游只能猜，而猜错不报错。

⚠️ 本条是**程序**不是断言，**无机械判据**；跑没跑要写进该阶段的 `VERIFICATION.md`，
不许因为「看起来工具不多」就默认通过。

### 8.2 `Refusal` 必须是封闭枚举，不是自由文本

harness 自己给了正解范例：`PreToolDecision` 是三分支联合
`allow | deny{reason} | ask{reason?}`，而且**没有任何分支能携带 args**
⇒ **「改写工具参数」在类型上不可表达**，不是运行时被拒。
本项目照此办理：`Refusal` 的理由码取自封闭枚举，
与 Phase 1 已建立的 `resolve.py` `RefusalCode` 模式一致（D-018 已在勾稽侧沿用同一模式）。

#### 8.2.1 枚举的**名字**必须是它能证明的那件事（2026-08-26 补，落地待办 L-11）

封闭枚举挡住了「取值超出词表」，**挡不住「词表里那个词说大了」**。

**实证**（`references/deepseek-harness-notes-part3.md` C-A10，源 `S-35:29`）：harness 在给一个
状态命名时明写 **`Naming it delivery would overstate the durable fact`**
——它只能证明「分派出去了」，证明不了「投递到了」，于是名字不许叫 delivery。
同源的第二条：**可见 ≠ 被读**。

⇒ **本项目的状态名与理由码，必须是该状态能被证据证明的那件事，不许取上位词。**
可机械化的一半：**每个枚举值旁必须写一句「它凭什么证据成立」**，写不出来就改名或删掉。
本项目已有的正面样本是 §8.3 的 `completed_degraded`——它拒绝把降级说成 `completed`，
正是这条规范的一次应用；本小节是把那一次应用**升格为对所有枚举命名的通则**。

具体到抽取侧的高危词：
`extracted`（真正能证明的往往只是「在页面上定位到了这一行」）、
`verified`（能证明的常常只是「勾稽等式在本批次成立」）、
`matched`（能证明的是「标签逐字命中」，不是「科目语义相同」）。

### 8.3 有一处**明确不抄**

harness 拒绝时只填 `error: { message }` 而无 `info`，落盘处 `...error?.info ? {...} : {}`
⇒ **durable 事件里连 `error` 字段都不出现**（`core/tools/src/index.ts:1496`）。
若照抄，**AC-05 就只能靠正则匹配一句自然语言来验**，
与 D-003「证据链是第一类产物、必须可机械复核」直接冲突。
**本项目的拒绝事件必须携带结构化理由码字段，且该字段不得因取值为空而从事件中消失。**

**补充（2026-08-22）——本节此前只管「拒绝」，不管「降级成功」，那是个洞。**
hello-agents 的 LangGraph 案例把**降级路径与正常路径写进同一个终态**
（两处都写 `step="completed"`，`references/hello-agents-ch06-frameworks.md` §5）
⇒ 事后无法区分「正常算出来的」与「兜底兜出来的」。
**这与「拒绝要留痕」是同一个要求的另一半：降级成功而不留痕，同样是证据链上的洞。**
本项目的终态因此必须至少三分：
`completed` ｜ `completed_degraded{cause: 封闭枚举}` ｜ `refused{code: 封闭枚举}`。
`completed_degraded` 的 `cause` 与 `refused` 的 `code` 取自**同一套封闭词表的不同分区**，
不得是自由文本。

#### 8.3.1 记进证据链的推理，必须是**产生那个动作的那一次**（2026-08-26 补，落地待办 L-67）

终态三分管的是「这次是怎么结束的」，本小节管的是「写在证据链里的理由是不是真的那条理由」。

**实证**（`references/hello-agents-framework-core.md` FC-B1，该文 §6.7(a)）：
hello-agents 的 `arun_stream` **每一步调用 LLM 两次**
（`react_agent.py:946-961` 流式、`:980-986` 非流式），
用户屏幕上读到的推理来自第一次采样，实际执行的 `tool_calls` 来自第二次（`:988`）。
`temperature > 0` 时两者**没有因果关系**，而代码注释自承这是「简化处理」（`:977-979`）。

**为什么这条比「证据缺失」更危险**：AC-05（字段齐全率 100%）在这种状态下**照样满分**
——字段全都在，只是它们描述的不是那次动作。
`PROJECT_SPEC.md` 的「AC-05 的已知盲区」一节已经把这个反例记为**盲区**；
本小节是那条盲区在架构侧的**约束**，两处配对使用：

> **证据链中记录的推理，必须与产生被记录动作的那次模型调用是同一次。**
> 判据可机械化：证据链条目须携带**同一个 `completion_id` / 请求哈希**；
> 推理与动作分属两次调用时**判为失败，不判为降级成功**（措辞直接沿用 D-003）。

⚠️ 本项目 Phase 1.5 的口径解析与勾稽全程不调模型，**该场景此刻不成立**；
这条是给 Phase 2 引入模型调用时的前置约束，**写在这里是为了不等到那时才想起来**。

### 8.5 证据指针必须被下游**强制消费**（2026-08-22 新增）

这是 §8.1「闸门放进调用签名」在**证据侧**的镜像，此前只有闸门那半边。

**实证**（`references/hello-agents-framework-tools.md` §9）：hello-agents 的
`truncator.py` 把工具输出全文写盘并返回 `{preview, full_output_path, stats}`
——**形状完全正确，只有 30 行**。但 `full_output_path` 在**唯二的两个调用点**
（`react_agent.py:847` / `:1224`）被丢弃，只取了 `preview`；
`grep -rnE 'tool_output_dir|tool-output'` 全包 **3 命中，全是写侧配置，零处读回**。
⇒ **全文确实写在磁盘上，但没有任何人知道它在哪。**

**结论不是「要存全文」，是**：存证机制做对了没用，**指针如果只是「可选返回值」，它一定会在接线时被丢掉**。
落到本项目：抽取记录与计算结果之间的引用（`field_id` + `page` + `anchor_page`）
必须出现在**函数签名的返回类型里且不可为空**，
不能做成「顺带塞进 metadata 的一个可选键」——那等价于没有。

**同源的第二个实证**：`core/agent.py:647-700` 的同步工具路径**从不调截断器**
（`grep -c "self.truncator.truncate"` = 2，都在 ReAct 的异步分支），
而 `truncator.py:4` 的文档写着「统一截断工具输出」——实际覆盖 2/6 调用点、1/4 Agent。
⇒ **凡是要求「每次都做」的事，不能放在调用点。**

**依据栏补充（2026-08-26，落地待办 L-20）——从「一次观察」升级为「已验证规律」。**
本节此前只有 `truncator.py` 一个实证，那只是**一次观察**。
`references/hello-agents-ch09-context.md` C9-B2 在**同一章内**又给了三个同源实例：

| # | 证据指针被生产在哪 | 谁消费了它 |
|---|---|---|
| 1 | `note_id` 写进笔记返回值（`ch9:1428`） | 无 |
| 2 | `source` 字段（`ch9:2012` / `:2018`） | 无 |
| 3 | `ContextPacket.metadata` 通道 | `_structure` **只读 `metadata["type"]`** |

⇒ **同一个病在一章里犯三次**，加上 `truncator.py` 共四个独立实例，
且四次的形状完全一致：**指针被生产、被放进一个可选位置、然后没有任何人读它。**
这不是某个作者的疏忽，是「可选返回值」这个形状本身的必然结果。
**本节的强度因此从「建议」提升到「结构性要求」**：
证据指针不进签名的返回类型，就一定会在接线时被丢掉。

#### 8.5.1 上游那一半：**留痕写不进去 ⇒ 决定作废**（2026-08-23 补，落地待办 L-1）

§8.5 此前**只写了下游**（指针必须被强制消费），**上游完全没写**：
如果证据根本没写进去，这条结论算不算数？

harness 的答案是**不算数**，而且理由不是「安全起见」，是**配对**——
`approval.md:122-126` 逐字：**返回一个没被记录的决定会破坏配对**
（`returning an unlogged decision would violate the pair`）；
配套的 `:117-119`：**一个 idle 的 ask 在追加任何东西之前就先拒绝**。

**本项目照此办理，并且必须明确提交点在哪**：

| 时机 | 规则 |
|---|---|
| **证据提交之前**失败 | **整体失败**。不产出结论，返回 `Refusal`，不得「先给答案后补证据」 |
| **证据提交之后**、观察者/下游失败 | **被 contain，不得反噬**已提交的证据。证据已经是事实，下游坏了是下游的事 |

⇒ **提交点是分界线**：它之前，任何失败都作废整个结论；它之后，任何失败都不许回改证据。
没有这条界线，「留痕失败」会滑成「降级成功」——而那正是 D-003 明令不接受的。

**与 §8.4 的关系**：§8.4 说的是 fail-closed 放在**读入**边界（消费侧），
本节说的是**写入**侧的作废规则。两者不冲突：读入侧防「用了没校验的证据」，
写入侧防「给了没有证据的结论」。

#### 8.5.2 指针必须说明**自己是怎么被选出来的**（2026-08-23 补，落地待办 L-2）

指针非空、且被下游消费了，**仍然可能是错的**——如果它是从一个被抽样/排序/截断过的
集合里挑出来的，而这三件事没有随结果一起呈现。

**实证**（`references/deepseek-harness-notes-part3.md` C-A1，源该文的 bug-fix 条目 `NP3-B10:15-17`）：
harness 的 glob 结果超上限时，页脚**明说**「这是跨条目抽样，不是按修改时间取的头部」，
并报告触及了多少个顶层条目；只要 spill 成功，**完整排序列表保留在 artifact 里**。
反面是三个**各自都正确**的行为合成一个假象：抽样正确 + 排序正确 + 截断正确
⇒ 读者以为看到的是「最相关的前 N 条」，实际是「某种抽样下的前 N 条」。

**本项目的同构面**：年报抽取里的「取前 N 行 / 按某列排序 / 页内截断」与它**逐项同构**。

> **编号说明**：`NP3-` 前缀是 `notes-part3` 自己的 bug-fix 条目编号，与本仓台账的 A 区 / B 区**无关**。加前缀是必须的——裸编号会被 `check_xrefs.py` 当成台账引用，写这一节时实地触发过一次（台账 N-36）。

⇒ **证据指针必须携带取数口径三元组**，且该三元组与指针一样不可为空：

```text
evidence_pointer = { field_id, page, anchor_page,
                     selection = { sampling, order_key, truncation } }
```

- `sampling` —— 这条是全量里的第几条，还是某种抽样的结果
- `order_key` —— 按什么排的序（表内行序 / y 坐标 / 表头匹配度…）
- `truncation` —— 在哪里被截断的，被截掉了多少

**配套判据（在 `EVAL_CASES` 侧）**：答案引用的表格片段若来自**截断页**而未声明口径，
**记失败**，不记「证据不足」——它不是证据少，是证据的含义被改了。

⚠️ **尚未实现**，且 `page` / `anchor_page` 之外的三元组字段**不在 D-019 的裁决范围内**，
落地时须确认是否构成对 D-019 的扩展。判据见 `LANDING-BACKLOG` L-2。

§8.5 到 §8.5.2 全是**纪律**——「必须被消费」「必须携带三元组」。

#### 8.5.4 审计事件 log-only，不进模型上下文（2026-08-26 补，落地待办 L-16）

**实证**（`references/deepseek-harness-docs-part2.md` HD2-19，源 `approval.md:88`）：
harness 的审批/审计事件是 **log-only** ——写进持久日志，**不回流进模型上下文**。

⇒ **本项目的证据链事件一律不得被塞回 prompt。** 三条理由，按重要性排序：

1. **破坏复核的独立性。** AC-06 要求复核者「仅凭证据链独立判断对错」。
   若证据链内容参与了产生答案的那次采样，答案与证据之间就有了循环依赖——
   复核者读到的「依据」是模型自己刚看过的东西，**一致不构成印证**。
2. **制造 §8.3.1 那类不同源。** 证据回流后，第二次采样看到的上下文与第一次不同，
   两次的推理不可比。
3. **费 token，且最先被裁掉。** 见 `references/hello-agents-ch09-context.md` A-7
   记的反例（`ch9:538` 的 `break` + `[Output]` 排在最后：**输出契约在预算紧张时最先被丢弃**）。

**配套约束**：`[Evidence]` 分区与输出契约分区**不参与预算裁剪**，裁剪只发生在证据条目内部
（见 §8.7）。

#### 8.5.5 关掉一个检查 ≠ 该检查从未存在（2026-08-26 补，落地待办 L-17）

**实证**（`references/deepseek-harness-docs-part2.md` HD2-20，源 `invariants.md:55`）：
harness 里**被过滤掉的注册仍然占住名字**——关掉不等于抹除。

⇒ **若将来做可配置关闭的口径校验，被关掉那条的标识必须仍出现在日志里**，
携带一个「本次被关闭」的显式取值。否则「关掉了 A」与「A 从未注册」在证据链上不可区分，
而这两件事对复核者的含义完全相反：前者是**有人做了决定**，后者是**没人想到这件事**。

**注意本条借的是什么、不借的是什么**（`references/README.md` 第 4 条）：
借的是「被关掉的东西仍然留名」，**不是**「口径闸门可以被关掉」。
本项目的口径闸门不可替换、不可绕过，那是它存在的理由——见 §8.1。

#### 8.5.6 不能证明因果时，证据链只能写「同一区间内发生」（2026-08-26 补，落地待办 L-15）

**实证**（`references/deepseek-harness-docs-part2.md` HD2-18，源 `defensive-patterns.md:15-17`）：
harness 明写要把选中的输出**描述为区间范围内的（interval-wide），而不是因果归因到那条消息**。

本项目的证据链默认「结论 ← 依据」是因果的。**并发取数时那个默认不成立**：
两条抽取记录落在同一个时间窗里，不代表后者用了前者。

⇒ **凡是无法证明因果的关联，证据链只许写「同一批次 / 同一区间内发生」，不许写成因果归因。**
判据：证据链条目里表达「因为」的字段（如 `derived_from`），
**其值必须能追到一次真实的读取动作**（读了哪条记录、在哪一步读的）；
追不到就只能落在表达「同现」的字段里。

⚠️ **本阶段场景不成立、但条文先写下**：Phase 1.5 是单公司单年顺序抽取，无并发；
这一条到 Phase 2 引入并发取数时才真正生效。
**先写下来的理由**是：并发是被「顺手加个线程池」引入的，
那一刻没有人会回头翻架构文档。

#### 8.5.7 证据落盘：内容寻址 + append-only + tombstone（2026-08-26 补，落地待办 L-71 / L-72）

> ✅ **2026-08-27：本节的四条约束已升格为 `D-027`**（操作者授权 agent 判断）。
> **本节保留的是论证与三处独立外部实证；约束本身的权威落点是 `D-027`。**
> 改动这四条须走决策变更流程，不能只改本节。
> 升格理由是**可逆性**：这是数据格式承诺，一旦落了盘，改动会作废所有已产出记录。

§8.5 到 §8.5.6 管的是**证据指针**，本小节管的是**指针指向的那个文件**。
两个独立实证，指向同一条约束：

**（a）时间戳精度决定持久化会不会互相覆盖**
（`references/hello-agents-framework-tools.md` FT-A7）：
`truncator.py:168` 用 `%Y%m%d_%H%M%S_%f`（带微秒）是全仓唯一做对的；
而 `DevLogTool` 与 `TodoWrite` 用固定名或秒级名，**同秒内第二次写覆盖第一次**。
**一个证据文件被覆盖，和没写过没有区别。**

**（b）记录系统若无法区分「记录里没有」与「记录被清掉了」，它防不住审计要防的那件事**
（`references/hello-agents-framework-tools.md` FT-B7）：
`DevLogTool` 是固定文件名 + `except Exception: pass` + **`clear` 不留痕**。
该文自己的判断是「A4（`clear` 不留痕）单独就足以否决」。

⇒ **本项目的证据落盘三条约束**：

1. **内容寻址** —— 文件名用内容 SHA-256 前缀，**不用时间戳**。
   比微秒更强，且天然幂等：同一份内容写两次就是同一个文件，不会产生第二份拷贝。
2. **append-only** —— 已提交的证据不可原地改写（与 §8.5.1 的提交点分界线是同一条）。
3. **删除只能写 tombstone** —— 记一条「这条在何时被谁以什么理由标记失效」，
   **不许覆盖或移除原记录**。

4. **id 单调不复用** —— **禁止用集合长度参与 id 构造**（2026-08-27 补，落地待办 `L-79`）。

   第三个独立实证（`references/hello-agents-ch09-context.md` C9-B6，
   `ch9:980` / `note_tool.py:118-122` + `:407-410`）：
   id 是 `{时间戳}_{len(index)}`，而 `delete` **会让 `len` 变小**
   ⇒ **同一秒内删一条再新建，新建的那条会拿到刚被删掉那条的 id**；
   `create` 随后**直接覆盖文件与索引，全程静默**。

   **对「id 即证据指针」的系统，id 可复用是致命属性**，不是缺陷等级的问题：
   一条证据链引用了 `note_x`，而 `note_x` 此刻指向的是另一份内容——
   **指针还在、指向变了，且没有任何一层会报错**。
   这比 §8.5 记的那四个「指针被生产、无人消费」更坏：那四个是指针没人用，这个是指针在骗人。

   ⇒ 上面 1、2、3 三条**在构造上已经排除了它的两个前提**，但必须写出来：
   - **内容寻址**（第 1 条）⇒ id 是内容的函数，**同一个 id 只可能对应同一份内容**；
   - **append-only + tombstone**（第 2、3 条）⇒ 集合长度**只增不减**，
     那个「`len` 变小」的机制根本不存在。

   **为什么仍要单列一条**：前两条是**关于存储的**约束，这一条是**关于 id 生成的**约束。
   一个「按内容寻址落盘、但索引另用自增计数命名」的实现能同时满足 1、2、3 而违反本条
   ——那正是命中面：抽取记录若用 `批次内序号` 编号，
   而序号取自「当前已抽取条数」，一次重跑就会复用。
   ⇒ **id 只允许两种来源**：内容摘要，或**单调自增且持久化的序列**。
   **禁止任何形式的 `len(collection)` 参与 id。**

⚠️ **这四条目前是架构约束，不是决策。** `D-003` 规定了「证据链是第一类产物」与字段固定，

### 8.7 回答上下文的固定分区模板（2026-08-26 新增，落地待办 L-75）

**实证**（`references/hello-agents-ch09-context.md` C9-A6，`ch9:135`）：
书稿给的固定骨架是 **Role / Task / State / Evidence / Context / Output** 六分区。

「这次少了哪一段」是可判定的，而不是靠读一遍散文去感觉。

⇒ **本项目的回答上下文采用固定分区，且加两条本项目特有的约束**：

1. **`[Evidence]` 的每一条必须带 `field_id` 前缀。**
   没有前缀的行不算证据，装配时直接拒绝——
   这是 §8.5「指针必须被强制消费」在**上下文装配**这一步的落点。
2. **`[Evidence]` 与 `[Output]` 两个分区不参与预算裁剪。**
   反例出处同章 A-7（`ch9:538`）：书稿的 `break` 让 `[Output]` 排在最后、
   **在预算紧张时最先被整段丢弃**——即**越是要紧的契约越先被裁掉**。
   裁剪只允许发生在**单条证据条目内部**，且必须按 §8.5.2 报告 `truncation`。

**与 §8.5.4 的关系**：那一节说审计事件不进上下文，本节说证据分区不许被裁——
两者不矛盾：**进上下文的是证据指针与被引用的原文片段，不是审计事件流。**
