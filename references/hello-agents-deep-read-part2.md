## 2. Ch12 结论

### 2.1 章节骨架

第十二章叫「智能体性能评估」，正文 2743 行，结构是**三个具体基准的实操**，不是一套评估方法论：

- 12.1 评估基础（为什么评、有哪些基准、本章选哪三个）
- 12.2 **BFCL** —— 工具调用能力，AST 匹配
- 12.3 **GAIA** —— 通用助手能力，准精确匹配（Quasi Exact Match）
- 12.4 **数据生成质量评估** —— LLM Judge + Win Rate + 人工验证（用 AIME 数学题做载体）

选这三个的理由写在 L93–106：BFCL「数据集规模适中，评估指标清晰，社区活跃」；
GAIA「任务真实，难度分级，综合性强」；数据生成评估「可以完整体验如何使用 Agent 创造数据」。

### 2.2 必答问题 1：评估分成哪几个维度/层次？判定方式是什么？

**原文没有给「层次/维度」的正式分类框架**，它给的是两组并列清单：

**（a）按能力域分的基准清单（L58–81）**，三类：
1. 工具调用能力评估：BFCL、ToolBench（清华，16000+ 真实 API）、API-Bank（MSR，53 个 API）
2. 通用能力评估：GAIA、AgentBench（清华，8 个领域）、WebArena（CMU，网页环境）
3. 多智能体协作评估：ChatEval、SOTOPIA、自定义协作场景

**（b）按指标类型分的四类（L82–89）**：
- 准确性指标：Accuracy / Exact Match / F1
- 效率指标：Response Time / Token Usage
- 鲁棒性指标：Error Rate / Failure Recovery
- 协作指标：Communication Efficiency / Task Completion

**判定方式**在本章实际落地为三种，分别对应 12.2/12.3/12.4：

| 判定方式 | 用在哪 | 具体算法 |
|---|---|---|
| 规则（程序化） | BFCL | AST 匹配（`ast.dump` 比较，L835–860） |
| 规则（程序化） | GAIA | 准精确匹配 Quasi Exact Match |
| 模型判分 | 数据生成质量 | LLM Judge（多维度打分）、Win Rate（成对比较） |
| 人工 | 数据生成质量 | 人工验证界面（12.4.6，Web UI） |

关键观察：**「规则判定」只用在有 ground truth 的封闭题上，「模型判分」只用在无标准答案的生成质量上。**
两者在本章里不混用——没有出现「用 LLM judge 去判 BFCL 的对错」这种设计。这一点对 finaudit 是正面参考。

原文对「智能体评估与传统软件测试的区别」给了三条（L50），值得抄：
输出的不确定性（同一问题可能有多个正确答案）、评估标准的多样性（工具调用查函数签名 / 问答查语义相似度）、
评估成本高昂。

### 2.3 必答问题 3（先答，因为涉及核实上一轮的两条断言）

**断言 A：「单次评估成本可能数百元」——属实，但措辞要收紧。**

原文 L50：

> 最后是评估成本的高昂，每次评估都需要大量的 API 调用，成本可能达到数百元甚至更多。

这是 12.1.1 里论证「智能体评估难」的第三条理由，**是一句定性提醒，不是实测数据**——
全章没有给出任何成本核算表、token 计费公式或实跑账单。所以引用时应写成
「教材提示单次全量评估的 API 成本可能达数百元量级」，不能写成「实测数据显示…」。

**断言 B：「渐进式评估：先 5 个样本，>0.8 才扩」——属实，出处 12.2.6 L916–931。**

原文给的是可执行代码，门槛就是 0.8：

```python
# 第一步：快速测试（5个样本）
results_quick = bfcl_tool.run(agent, category="simple_python", max_samples=5)

# 第二步：中等规模测试（50个样本）
if results_quick['overall_accuracy'] > 0.8:
    results_medium = bfcl_tool.run(agent, category="simple_python", max_samples=50)

# 第三步：完整评估（全部样本）
if results_medium['overall_accuracy'] > 0.8:
    results_full = bfcl_tool.run(agent, category="simple_python", max_samples=0)
```

需要指出的是：**这是「省钱的筛选闸门」，不是统计上成立的早停。**
5 个样本上的准确率，其 95% 置信区间宽到几乎无信息量（5/5 的下界也就 0.48 左右），
用 0.8 当阈值在 n=5 时等价于「≥4/5 就继续」。原文没有讨论这个问题，也没有提置信区间。
finaudit 若要抄这个模式，必须自己补上「小样本闸门只用于止损，不用于下结论」的约束。

**效率度量本身**：12.1.2 L87 把 Response Time 与 Token Usage 列为效率指标，
但 12.2/12.3/12.4 的**评估器输出里我没有读到这两项被真正计算或写进报告**——
BFCL 报告字段是 overall_accuracy / correct_samples / total_samples（L447–448、L525–536），
没有耗时与 token 统计。（GAIA/数据生成两节读完后回填确认。）

### 2.4 必答问题 5：公认基准与 BFCL 的 `irrelevance` 类别

**提到的公认基准（L62–79）**：BFCL、ToolBench、API-Bank、GAIA、**AgentBench**、WebArena、ChatEval、SOTOPIA。
**τ-bench 未出现**（我在 ch12 全文未读到；全库检索留待 §6 说明）。

**`irrelevance` 类别属实，且原文明确点出它的语义就是「判断是否真的需要调用工具」。** 四处出处：

- L62：BFCL「涵盖 simple、multiple、parallel、irrelevance 四个类别」
- L172：「最后是需要判断是否需要调用函数的场景（Irrelevance）」
- L908：「在 irrelevance 场景下需要判断是否真的需要调用工具」
- L938：多类别评估代码里 `categories = ["simple_python", "multiple", "parallel", "irrelevance"]`

**对上一轮「我们的 C2 拒答边界有此先例」的核实结论：方向成立，但先例比我们需要的弱。**
BFCL 的 irrelevance 判的是「该不该调工具」，我们的 C2 判的是「该不该给答案」，
两者都是「正确的行为是不动作」，这一层类比站得住。
但**原文并没有说明 irrelevance 类别怎么计分**——没有给该类别的指标定义，
也没有说不调用工具时 AST 匹配函数如何取值（`AST_Match` 在 L234–238 只定义了匹配/不匹配两种情况）。
而且 12.2.6 L904 自陈**本章实现只测了 simple_python 等基础类别，irrelevance 属于「还需要针对性优化」的未做项**。
所以：可以引用 BFCL 作为「拒答类目有基准先例」的依据，**不能**引用它作为「拒答如何计分」的方法依据。

### 2.5 必答问题 4：非二元判定（拒答 / 不适用 / 无法判断）

**结论：三种基准里只有 Win Rate 与人工验证有非二元判定；两个规则型基准都是严格二元、分母恒为 N。**

| 判定体系 | 取值 | 分母处理 |
|---|---|---|
| BFCL AST 匹配 | `{0,1}`（L234–238） | Accuracy = 对 N 个样本求均值（L277）；`Error Rate = 1 - Accuracy`（L319）。**没有「不适用」出口** |
| GAIA 准精确匹配 | `{0,1}`（L1045–1049、L1610） | Exact Match Rate = 对 N 求均值（L1080）；分级准确率按 Level 分桶（L1094） |
| GAIA「部分匹配」 | 名义上是第二档 | **原文从未定义它怎么算**（见下） |
| Win Rate | **三值 Win / Loss / Tie**（L1898、L2293） | 三者同分母，`Win+Loss+Tie = 100%`（L1920） |
| 人工验证 | **三态 approved / rejected / needs_revision**（L1932–1935、L2346） | 原文未给出这三态如何汇总成指标 |

三条必须记下来的细节：

**（a）GAIA 的「部分匹配率」是个悬空指标。** `partial_match_rate` 出现在工具返回值（L1336）、
运行日志（L1370）、报告模板（L1437–1439、L1445）和样本表格列头（L1449）里，
但 `GAIAEvaluator.evaluate` 的伪代码只算了 `exact_match`（L1610–1618），
`generate_report` 的模板里也**只有** exact 字段（L1789–1818）。
而且在所有出现过的数字里，部分匹配率**恒等于**精确匹配率（80%/80%，50%/50%）。
**结论：这是一个声明了但没有独立定义、也从未产生过不同取值的第二档。**
finaudit 若要设「部分正确」档，必须先定义它的判据，否则就会复制这个空壳。

**（b）Win Rate 的 Tie 桶被判分失败污染了。** 这是本章最值得警惕的一条，
证据在实跑产物 `win_rate_report_20251011_124322.md`：

```
### 对比 2
- **胜者**: 🤝 Tie
- **理由**: Failed to parse response
```

判分模型的输出没解析成功，这条被**静默计入 Tie**，并且照常进入分母。
该次运行 20 次对比里 Tie 共 2 次（10%），其中至少 1 次是解析失败——
**即「平局率」里有一半其实是「判不出来」。** 两种语义完全不同的事件被合并进同一个桶。
原文正文对此只字未提。

**（c）三态人工验证没有接回指标。** 12.4.6 定义了 approved/rejected/needs_revision
（L2346）并存进 `<data_path>_verifications.json`（L2386–2401），
但 12.4.7 的 `run_complete_evaluation`（L2409–2485）**完全没有读取人工验证结果**，
12.4.8 的综合报告里也没有人工验证章节。人工验证在流程图里存在，在数据流里断开——
它被降级成 12.4.8「下一步行动」里的一句建议（L2640、实跑产物同样如此）。

### 2.5bis 必答问题 2：LLM-as-judge 怎么做的？同源问题？校准？

**做法（12.4，唯一使用模型判分的地方）**，两种：

1. **LLM Judge —— 绝对打分。** 单题四维各 1–5 分：正确性 / 清晰度 / 难度匹配 / 完整性，
   要求 JSON 输出 `{correctness, clarity, difficulty_match, completeness, comments}`（提示词 L2127–2152）。
   汇总成三个指标（L1863–1878）：平均分、及格率（题均分 ≥3.5）、优秀率（题均分 ≥4.5）。
2. **Win Rate —— 成对比较。** 把「生成题目」与「AIME 真题」并列给判分模型，
   要求输出 `{"winner": "A" 或 "B" 或 "Tie", "reason": ...}`（提示词 L2273–2296）。
   理想值被定义为 **Win Rate ≈ 50%**（L1889、L1922）。

**同源问题：存在，而且是最严重的一种——判分者与被判者是同一个模型，原文完全没有处理。**

- 生成侧：运行日志 L2527 明确写 `生成模型: gpt-4o`
- 判分侧：`run_complete_evaluation` 里两个工具都传 `"judge_model": "gpt-4o"`（L2447、L2462），
  实跑产物 `llm_judge_report_*.md` 与 `win_rate_report_*.md` 的元数据都记着 `**评委模型**: gpt-4o`
- 代码层面更直接：`llm = HelloAgentsLLM()` 这**同一个对象**先喂给 `AIMEGenerator`，
  再喂给 `LLMJudgeTool(llm=llm)` 和 `WinRateTool(llm=llm)`（L2436、L2441、L2456）

也就是说 **gpt-4o 在评判 gpt-4o 自己生成的题目相对于真题的优劣**，而 Win Rate 的设计意图
恰恰是「相对真题的质量差距」。正文没有任何一句提示这个风险。

**校准：没有。全 16 章 `校准` 零命中**（我对 `ch01_zh.md`…`ch16_zh.md` 全部做了正则检索）。
同样零命中的还有：`位置偏差 / position bias / 顺序偏`、`自我偏好 / self-preference`、
`kappa`、`污染 / contamination`。没有judge 与人工标注的一致性检验，没有judge 复测/自洽性检验，
没有多judge 交叉。`一致性` 在 ch12 只出现 1 次（L1850），且是**宣称** LLM Judge
「能保持评估标准的一致性」这一好处，不是测量出来的一致性。

**位置偏差：正文有隐患，但实跑产物显示实现里可能已经打乱了 A/B——两者互相矛盾。**
正文提示词把位置写死（L2275–2280：【题目A - 生成题目】/【题目B - AIME真题】），
如果照此实现，判分模型永远知道 A 是被测方，这是教科书级的位置偏差 + 身份泄漏。
但实跑产物里，10 条明细中有 **6 条**的「生成题目」字段装的是纯数字 id（真题的 id 格式），
「参考题目」字段装的却是 `gen_aime_*`（生成题的 id 格式）：

### 2.6 必答问题 6：数据集构造与「题目独立于实现」

12.2 的做法是**完全外部化数据集**，这一点做得比较干净：

- 数据集不自己造，直接 `git clone https://github.com/ShishirPatil/gorilla.git`，
  从 `bfcl_eval/data/` 与 `bfcl_eval/data/possible_answer/` 读测试数据与 ground truth（L365–377）
- 明确推荐这种方式的理由（L379）：「包含完整的 ground truth，数据格式与官方评估工具完全一致，
  可以直接使用官方评估脚本，并且支持 BFCL v4 最新版本」
- 更强的一步：**判分也外部化**。`BFCLEvaluationTool` 默认 `run_official_eval=True`，
  自动把结果导出成官方 JSONL 格式、复制到 `result/{model_name}/`、然后 shell 调用
  `bfcl evaluate --model ... --test-category ... --partial-eval`（L648–660、L688–693）

**这是本章对 finaudit 最有价值的一条结构性经验：题目与判分器都不由被测方持有。**

GAIA 走得更远一层——**它是 gated dataset**：必须先在 HuggingFace 申请访问权限、拿 `HF_TOKEN`
才能下载（L1197–1204）。而且**测试集不给答案**，只能导出 JSONL 提交到官方 leaderboard
由官方判分（L1473–1497）。`metadata.jsonl` 里 validation 165 题、test 301 题（L1249–1253），
本地能自评的只有 validation。这是「防题目泄漏」的强机制：被测方拿不到 test 的 ground truth。

12.4 的数据生成评估则是**自己造题、外部对标**：题目由 gpt-4o 现生成，
但**参照物**是外部真题——生成时的风格参考取自 `TianHongZXY/aime-1983-2025`（963 道，L2523），
评估时的对手取自 `math-ai/aime25`（L2239）。原文特意说明「生成阶段用 1983–2025，
评估阶段只与 2025 真题比」（L2500–2503），即**参考样例池与评估对照集刻意错开**，
避免拿同一批题既当范例又当考题。这个「构造集 / 对照集分离」的思路值得抄。

**但整章没有任何冻结机制，这一点必须明确记下：**

- `冻结`、`哈希 / SHA-256`、`污染 / contamination` 三组词在 ch12 **全部零命中**
- BFCL 是 `git clone` 最新 main，没有 pin commit，也没记录评估时的数据版本；
  正文反而把「支持 BFCL v4 最新版本」当成优点（L379）——「最新」正是不可复现的反面
- GAIA 用 `snapshot_download` 不带 revision 参数（L1559–1564），同样跟随最新
- 没有一处讨论训练数据污染。BFCL 与 AIME 真题都长期公开在 GitHub/HuggingFace 上，
  被测模型（gpt-4o / Qwen3-8B）见过的可能性很高，而 12.2.3 的实跑结果正是 **5/5 = 100%**
  （产物已核），这个满分**不能**排除记忆效应

**对 finaudit 的直接含义：hello-agents 能提供「题目与判分外部化」的架构参考，
但提供不了「可复现」的参考——它缺的正是 D-012 冻结校验那一层。**

### 2.7 实现细节的可信度：**教材正文的代码块不能当实现读**

12.2.5「核心组件实现细节」给的代码与前文自相矛盾，至少两处：

1. `BFCLDataset.__init__` 在 L726 的签名是 `(category="simple", local_data_path=None)`，
   而 12.2.2 L389 的实际调用是 `BFCLDataset(bfcl_data_dir=..., category="simple_python")`——
   参数名 `local_data_path` vs `bfcl_data_dir` 对不上。
2. `BFCLEvaluationTool.run` 在 L879 的签名是 `run(self, parameters: Dict)`，
   而全章所有调用都是 `run(agent=..., category=..., max_samples=...)`（L440、L639、L700、L922）。

L722、L745、L816、L866 这几个代码块用的是四反引号 ` ```` `，是文档拼接的痕迹。
结论：**12.2.5 是示意性伪代码，真实实现在 `hello_agents/evaluation/benchmarks/bfcl/`（本机不可读）。**
引用其实现细节时必须标注这一点。

一个具体的技术观察（若真按 L835–860 实现则是 bug）：`_ast_match` 用
`ast.dump(pred_args) == ast.dump(true_args)`，而 `_args_to_ast` 是把参数 `repr()` 后拼成
`func(k=v, ...)` 再 parse。这样得到的 AST **保留了字典的插入顺序**，
所以 `ast.dump` 字符串比较**恰恰不能**忽略参数顺序——与它自己注释里第 1 条
「忽略参数顺序：func(a=1, b=2) 等价于 func(b=2, a=1)」矛盾；
同理 `repr(2+3)` 在 Python 侧早就求值成 `5`，注释第 2 条「识别等价表达式」也不是这段代码实现的。
**真正的顺序无关与表达式等价必须在字典层面排序 / 求值后比较，这段示意代码做不到。**
finaudit 若做类似的「口径等价判定」，不要照抄这个 `ast.dump` 比较法。

### 3.1 Ch14 —— 与 finaudit 最相关的一章，也是最需要引以为戒的一章

**它做的事和 finaudit 表面上很像**：把一个复杂问题拆成子任务，逐个检索、总结，
最后生成一份带「参考文献」的结构化报告。开篇 L5 就说难点在于
「用户对引用来源的高要求」，L25 把「**可追溯**：记录所有搜索结果和来源，方便验证和引用」
列为三大核心能力之一。

**三阶段流程**（14.2.2）：规划 → 执行 → 报告。
规划 Agent 把主题拆成 3–5 个子任务，每个子任务是 `{title, intent, query}` 三字段 JSON（L265–283）；
执行阶段对每个子任务搜索（默认 `max_results: 5`）、调总结 Agent、存进 NoteTool（L293–337）；
报告阶段把所有子任务总结拼成最终报告（L393–427）。
三个 Agent 各司其职：Research Planner / Task Summarizer / Report Writer（14.3.1）。
落盘结构是 `workspace/notes/{task_id}.md` + `workspace/reports/final_report.md`（L984–993）。

**但它的「引用」是不可信的，这是本章对 finaudit 最重要的一条负面教训。** 三处证据：

**（a）来源编号 grounded，但引用与论断的对应关系无人校验。**
`_format_sources` 把搜索结果编号成 `[idx] title / URL / 摘要`（L620–629），
提示词要求「为每个观点添加来源引用（使用[1]、[2]等标记）」（L562、L567）。
所以 `[1]` 确实对应 `search_results[0]`。**但没有任何一行代码检查
「打了 [1] 的那句话是否真的被 source 1 支持」，也没有检查编号是否越界。**
标记完全由 LLM 自由生成，属于 prompt 层的约定，不是可执行的约束。

**（b）「参考文献」列的是检索到的全部来源，不是实际被引用的来源。**
`SummarizationService.summarize_task` 的文档把职责 4 写成
「**提取来源引用**：从总结中提取来源引用」（L1317、L1360），但代码是：

```python
# 提取来源URL
source_urls = [result["url"] for result in search_results]
```

（L1376–1377）——**它根本没有解析 summary，而是把喂进去的 5 条搜索结果 URL 原样返回。**
描述与实现直接矛盾。后果：报告末尾的参考文献是「我搜到过什么」，
不是「我用了什么」，更不是「这句话依据什么」。**这正是 D-003 说的「给不出证据链就算失败」
的反面样本——它给出的是证据链的外观。**

**（c）证据基座只有搜索摘要，不是原文。** 喂给总结 Agent 的是 `snippet`（L626–627），
且再被 `limit_source_tokens` 截断到 2000 token（约 8000 字符）后加 `"..."`（L958–971）。
没有抓取网页正文。所以整份报告建立在搜索引擎的摘要之上，
而截断本身可能把被引用的那句话切掉，且截断不留痕迹。

**（d）同一个类在两处给出不同签名。** 14.3.1 的 `summarize_task` 返回 `summary`（L606、L618），
14.5.2 的返回 `(summary, source_urls)`（L1352、L1379）。与 Ch12 一样，
**正文代码块是示意，不能当实现读**。

**可以借鉴的部分**：把「研究」拆成规划/执行/报告三段、每段一个窄职责 Agent，
每个子任务的中间产物单独落盘（notes/1.md…）便于事后追溯，
以及 SearchService 作为中间层不让 Agent 直接调工具、
「使得 Agent 更加专注处理得到的信息」（L1502）——这条对 finaudit 的确定性数据层是同向的。

### 3.2 Ch13 —— MCP 集成与共享实例，是可直接迁移的工程模式

13.4 是这一章唯一对 finaudit 有迁移价值的部分。

**为什么用 MCP 而不是直接调 HTTP API**（13.4.1，L667–673）四条理由：
Agent 失去自主决策能力（直调 API 就退化成函数调用）、参数传递复杂（高德 POI 搜索十几个参数
都要写进提示词）、响应解析困难、工具管理混乱。

**`MCPTool` + `auto_expand=True`**（L700–706）：一个 MCPTool 对象自动展开成 16 个独立 Tool
（L722–725）。底层是 JSON-RPC over stdin/stdout 的进程间通信，不是 HTTP（L713、L738–768）。

**13.4.3 共享 MCP 实例**——这条最值得记：三个 Agent 都要用高德工具时，
**不要各建一个实例**，否则会起三个服务器进程、独立打 API、
「可能会超过 API 的速率限制」（L778）。正确做法是在父 Agent 构造函数里建一次，
`add_tool(self.mcp_tool)` 分发给各子 Agent（L784–820）。
对 finaudit 的含义：数据源连接（AKShare / PDF 解析器）应当是单实例共享，
限流与配额在这一层集中控制，而不是每个 Agent 自己连。

13.4.4 还有一条诚实的坦白：Unsplash「是国外的服务…所以搜索结果可能不够准确」（L826）。

### 3.3 Ch15 —— 只有一个成本控制模式值得记

15.2.4「批量对话生成：轻负载模式」（L317–363）：把 N 个 NPC 的对话请求
**合并成一次 LLM 调用**，让模型一次返回 JSON `{"张三": "...", "李四": "..."}`，
声称「成本降低到原来的 1/3」（L331）。这是本书里唯一一处主动的 LLM 成本优化手段。
注意它的代价：一次调用的失败会同时打掉 N 个结果，且 `json.loads(response)` 无 try（L360）。

其余部分（好感度系统、Godot 场景、GDScript 前端）与 finaudit 无关。

### 4.1 Ch4.3 Plan-and-Solve（读了 L586–735、L810–868）

补上了此前只从小结获知结论的空洞。**形式化定义**（L603–615）：

- 规划：$P = \pi_{\text{plan}}(q)$，一次 LLM 调用产出 $n$ 步计划
- 执行：$s_i = \pi_{\text{solve}}(q, P, (s_1,\dots,s_{i-1}))$，最终答案取 $s_n$

与 ReAct 的分工被讲得很清楚（L590）：ReAct 像侦探随现场调整方向，
Plan-and-Solve 像建筑师先出蓝图再施工。**动机**是解决思维链在多步问题上「偏离轨道」（L594）。
适用场景 L622–626 明确列了「**需要整合多个信息源的报告撰写**：需要先规划好报告结构
（引言、数据来源A、数据来源B、总结），再逐一填充内容」——这正是 finaudit 的形状。

**工程上值得抄的一点**：规划器强制输出 ` ```python [...] ``` ` 包裹的 Python 列表，
再用 `ast.literal_eval` 安全解析（L644–655、L691–693），并对
`ValueError / SyntaxError / IndexError` 分别兜底返回 `[]`（L695–698）。
理由说得很实在：「强制要求输出为一个 Python 列表格式的字符串，
这极大地简化了后续代码的解析工作，使其比解析自然语言更稳定、更可靠」（L661）。

**两条必须记下的局限：**

1. **没有重规划。** 计划一旦生成就固定，执行器只能顺着走。L866 明确说
   「智能体一旦完成了任务，其工作流程便告结束」，Reflection（4.4）是作为**事后**补丁引入的，
   不是执行中的重规划。对 finaudit 的含义：若中途发现某张表取不到数，这个范式没有退路。
2. **4.3.4 的运行实例是退化的，不能作为该范式有效的证据。** 看 L821 生成的计划：
   `["计算周一卖出的苹果数量： 15个", "计算周二卖出的苹果数量： 周一数量 × 2 = 15 × 2 = 30个", ...]`
   ——**规划器在写计划时就把答案算完了**（30、25、70 都写在计划字符串里）。
   于是执行阶段 4 次 LLM 调用（L830–852）做的只是把计划里已有的数字抄出来。
   L861 却把它解读成「步骤2正确地使用了步骤1的结果」。**这个 demo 没有验证任何东西，
   只多花了 4 次调用。** 引用 Plan-and-Solve 时不要引用这个例子。

### 4.2 Ch10.3 A2A / 10.4 ANP（读了 L1108–1202、L1655–1729）

**A2A**（10.3.1）：解决 Agent 之间的协作，与 MCP（Agent↔工具）互补。
论点是中央协调器（星型拓扑）有三个问题——单点故障、性能瓶颈、扩展困难（L1116–1120），
A2A 改用 P2P 网状拓扑。核心抽象是 **Task 与 Artifact**（L1122），
并为 Task 定义了标准生命周期：创建/协商/代理/执行中/完成/失败（L1129）。
请求生命周期四步：代理发现 → 身份验证 → 发送消息 API → 发送消息流 API（L1139）。

**一个必须记下的诚实声明**（L1148）：「A2A 现有实现大部分为 `Sample Code`，
并且即使有 Python 的实现也较为繁琐，因此这里我们**只采用模拟协议思想的方式**」。
**所以本书的 A2A 章节不是真实协议实现，是示意。** 引用时不能说「hello-agents 实现了 A2A」。

**ANP**（10.4.1）：面向大规模开放网络，解决服务发现 / 智能路由 / 动态扩展（L1663–1669）。
三段机制（L1688–1694）：
1. 发现服务爬取各 Agent 的标准端点 `.well-known/agent-descriptions` 建索引
2. **基于 DID 的身份验证**——请求方用私钥对含自身 DID 的请求签名，接收方解析 DID 取公钥验签，
   「验证签名的真实性与请求的完整性」
3. 标准化接口执行

服务注册时带 `metadata={"load":0.3, "price":0.01, "version":"1.0.0"}`（L1707–1725），
即路由可依据负载与价格选择。

**对 finaudit 有启发的是第 2 条**：用非对称签名让一条结论**自带出处与完整性证明**，
接收方无需信任发送方即可验证。这与 D-003 的证据链是同构的思路，
虽然 DID 那一整套对本项目过重，但「结论 + 签名 + 可独立验签」的形状值得记。

### 4.3 Ch1.4（读了 L516–577）

**1.4.3 Workflow 与 Agent 的差异**，一句话定义（L549）：
「Workflow 是让 AI 按部就班地执行指令，而 Agent 则是赋予 AI 自由度去自主达成目标。」

它举的 Workflow 例子恰好是财务场景（L556）：**费用报销审批流程**——
金额 <500 由部门经理审批，>500 再加财务总监，「每一步、每一个判断条件都被精确地预先设定」。
Agent 的例子则强调「没有任何写死的 `if 天气=晴天 then 推荐颐和园` 的规则」（L564）。

**这对 finaudit 的定位很有用，但结论要反过来用**：本项目里
「用哪张表、哪个口径、依据哪条准则」恰恰**应该**是 Workflow 那一侧（确定性、预先定义、可复核），
只有「理解用户问的是什么」「组织解释」才在 Agent 那一侧。
本书把 Agent 的自由度当成核心价值（L564：「基于实时信息进行动态推理和决策的能力，
正是 Agent 的核心价值所在」）——**finaudit 不能整段照搬这个价值主张**，
我们的价值恰恰在于把可审计的那部分锁死。

### 4.4 Ch2.1（读了 L38–118）

这一节比我预期的有用，因为 finaudit 的准则层本质上就是个专家系统。

**MYCIN**（2.1.2，L61–73）：约 600 条 IF-THEN 规则，**反向链**推理
（从「确定致病菌」这一目标反推需要哪些证据，再向医生提问）。
**最值得记的是它的不确定性处理**：引入**置信因子（Certainty Factor, CF）**，
用 −1 到 1 的数值表示结论可信度，「使得系统能够处理不确定的、模糊的医学知识，
并给出带有可信度评估的诊断结果，这比简单的布尔逻辑更贴近现实世界」（L72）。

**这是全书唯一一处认真处理「非二元结论」的地方，而且它在 1970 年代。**
对照 Ch12 的评估体系——BFCL/GAIA 都是 {0,1}，Win Rate 的 Tie 桶还混进了解析失败——
**MYCIN 的 CF 比本书第 12 章的判定粒度更细。** finaudit 若需要「结论 + 置信度」的表达，
CF 是比本书评测章更好的参照，且可直接引 MYCIN 原始文献。

**2.1.4 符号主义的两类根本挑战**（L101–117），这是给准则规则库的预警：
- **知识获取瓶颈**：规则要靠专家访谈逐条编码，成本高、难规模化，
  且「人类专家的许多知识是内隐的、直觉性的，很难被清晰地表达为 IF-THEN 规则」
- **常识问题**：未显式编码的常识系统一无所知（Cyc 数十年成果仍有限）
- **框架问题**：动态世界里判断「哪些事物没变」在计算上不可行
- **系统脆弱性（Brittleness）**：「一旦遇到规则之外的任何微小变化或新情况，
  系统便可能完全失灵」；SHRDLU 之所以成功「正是因为它运行在一个规则完备的封闭世界里，
  而真实世界充满了例外」（L117）

**对 finaudit 的直接含义**：会计准则规则库会撞上同样的墙。
应对不是「把规则写全」，而是**明确规则的适用边界，边界外走拒答（C2）而不是硬套规则**——
这也反过来支撑了 C2 拒答边界的必要性，其论据比 BFCL irrelevance 那条更强。

## 5. 对 finaudit 的可借鉴点与必须避开的坑

**每条都标了出处；没有原文依据的判断我不写。**

### 5.1 可借鉴（按可迁移程度排序）

1. **题目与判分器都不由被测方持有。** BFCL 的数据集 `git clone` 官方仓库、
   判分 shell 调用官方 `bfcl evaluate`（ch12 L365–377、L648–660）；
   GAIA 的 test 集干脆不给 ground truth，只能提交官方 leaderboard（L1473–1497）。
   → finaudit 的 EVAL_CASES 判分器应与被测 pipeline 分离，至少做到**判分代码不 import 被测代码**。

2. **构造集与对照集刻意错开。** 生成时参考 1983–2025 的 963 道真题，
   评估时只与 2025 真题比（L2500–2503）。
   → 我们造题用的年报样本与评测对照的年报样本必须分离，且写进协议。

3. **评估报告里逐样本并列「预测 / 标准答案 / 是否正确」**（BFCL 报告 L540–543，产物已核；
   GAIA 报告同构 L1449–1452）。报告自身可复核，不必回日志。
   → 直接可抄进 finaudit 的评测报告格式，再加上我们的「口径 / 准则条目 / 结果哈希」列。

4. **报告元数据记录判分模型。** 两份 LLM 判分产物都写了 `**评委模型**: gpt-4o`。
   → 抄，并且**补上本书漏掉的**：被测模型、数据集版本/commit、prompt 版本。

5. **渐进式评估当止损闸门。** 5 → 50 → 全量，阈值 0.8（L916–931）。
   → 可抄，但必须改写成「小样本只用于止损，不用于下结论」（原文没有这个约束，见 §2.3）。

6. **共享工具实例集中限流。** 三个 Agent 共用一个 MCPTool，避免起三个进程各自打 API
   超速率限制（ch13 L776–820）。
   → finaudit 的数据源连接与 PDF 解析器应单实例共享。

7. **强制结构化输出 + `ast.literal_eval` 安全解析 + 分类型异常兜底**（ch4 L644–698）。
   → 规划/口径选择这类需要机器消费的 LLM 输出照此办理。

8. **中间产物逐任务落盘**（ch14 `workspace/notes/{id}.md`，L984–993）。
   → 与证据链同向，可直接对应我们每个子问题的证据文件。

9. **MYCIN 的置信因子**（ch2 L72）作为「非二元结论」的参照，优于本书第 12 章的二元判定。

### 5.2 必须避开的坑

1. **「参考文献 = 检索到的全部来源」是伪证据链。**
   ch14 的 `source_urls = [r["url"] for r in search_results]`（L1376–1377）
   与它自己声称的「从总结中提取来源引用」（L1317）直接矛盾。
   → finaudit 的证据必须是**被实际使用的那一条**，且引用与论断的绑定要可机器校验。
   凡是「LLM 自己打的引用标记」都不算证据。

2. **judge 与被测同源。** gpt-4o 生成、gpt-4o 判分（L2527 vs L2447/L2462），全书无一处提示风险。
   → finaudit 的 LLM 判分必须与被测模型异源，并记录两者；否则结论不可用。

3. **判分失败被静默归入「平局/中立」。** Win Rate 产物里
   `胜者: Tie / 理由: Failed to parse response`。
   → 「无法判断」必须是**独立的第四类**，与「真平局」分开统计，且要单独报出现率。
   这条直接影响我们 C2 拒答边界的计分设计：**拒答、判不出、错答，三者不能混。**

4. **声明了却没定义的指标。** GAIA 的 `partial_match_rate` 从未被定义，
   且在所有输出里恒等于 exact（§2.5a）。
   → 任何进入报告的字段必须有可执行的定义，否则不要进报告。

5. **报告呈现层与实际语义脱节。** Win Rate 报告的「生成题目/参考题目」两列
   装的其实是 A 位/B 位占位者（§2.5bis 表）。
   → 证据链的呈现必须自证，不能要求复核者逆向 id 命名规则。

6. **正文示例数字是手写期望值，不是运行结果**（§2.5ter 对照表，最大差距是
   「质量优秀」vs「需要改进」）。
   → 我们自己的文档里，示例输出必须来自真实运行，或显著标注为「构造示例」。

7. **人工验证接了 UI 但没接回指标**（§2.5c）。
   → 人工复核结果必须进入评测分母，否则就是装饰。

8. **没有冻结机制。** 全章 `冻结/哈希/污染` 零命中，`git clone` 最新 main、
   `snapshot_download` 不带 revision（§2.6）。
   → hello-agents 在这一层给不了任何参考，D-012 那套得我们自己扛。

9. **教材正文的代码块普遍与调用处签名矛盾**（BFCL 两处、ch14 `summarize_task` 两个版本）。
   → 不要把本书代码块当实现引用，引用时必须标注「示意伪代码」。

10. **不要照抄 `ast.dump` 做等价判定**（§2.7）：它保留字典插入顺序，
    实现不了它自己注释里承诺的「忽略参数顺序」。

11. **Plan-and-Solve 无重规划**（§4.1），且教材 demo 是退化的。
    → 采用该范式需自行补重规划/失败退出。

12. **本书把「Agent 的自由度」当核心价值**（ch1 L564）。
    → finaudit 的价值主张相反，不要顺手继承这句话（§4.3）。

13. **Ch16 推荐选题里的「智能股票分析…提供投资建议」**（ch16 L67）
    → 这是我们明确不做的东西，可作为「不是什么」的反例。
