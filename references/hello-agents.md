## 1. 它的框架分层（第 7 章）

四层，「分层解耦、单一职责、统一接口」：

```text
core/     agent.py      抽象基类，强制统一契约
          llm.py        统一 LLM 接口
          message.py    标准消息格式（role 限四种，对齐 OpenAI 规范）
          config.py / exceptions.py
agents/   具体 agent 实现，继承抽象 Agent
tools/    ToolRegistry —— 注册、执行、管理
tools/builtin/  计算器、搜索等
```

`Agent` 抽象基类强制：统一初始化参数（name / llm / system_prompt / config）、
抽象 `run()` 作为唯一入口、`add_message()` / `get_history()` 管理对话历史。

## 2. 四个范式

| 范式 | 机制 |
|---|---|
| `SimpleAgent` | 基础对话，可选工具调用 |
| `ReActAgent` | 推理-行动循环，prompt 强制单步执行 |
| `ReflectionAgent` | 初次生成 → 自我反思 → 迭代改进 |
| `PlanAndSolveAgent` | 分解阶段（输出 Python list 格式的计划）→ 逐步执行 |

**对本项目**：主循环用 **ReAct**，外面套一层 **Reflection** 做「自查引用」——
「给出答案 → 反思引用的准则条号与口径版本对不对 → 修正」。
审计场景里这个回路是贴的，因为错误往往不在算术而在引错口径。

`PlanAndSolve` 暂不需要：本项目的问题多为单指标查询，不需要任务分解。

## 3. 刻意不借的：「万物皆 Tool」

它把 memory、RAG、RL 全部统一进 `ToolRegistry`，用一个概念覆盖所有扩展。
**对教学是好设计，对本项目是致命的。**

理由：如果口径查询只是「LLM 可以调的一个工具」，那 LLM 就**可以不调**——
直接用参数记忆答一个数出来。而「口径未定义时拒答而不是猜」是本项目的**全部论点**。
一个能被绕过的闸门等于没有闸门。

**本项目的做法**：语义层是**强制前置的闸门**，不是可选工具。
先解析口径 → 解析不到就拒答 → LLM 根本没机会开口。
具体形状见 `deepseek-harness.md` §3.1（`agent/pre-step` 的 reject 语义）。

这个偏离必须写进 Phase 2 的 `ARCHITECTURE.md` 并给出理由，
否则下一个人会以为是疏漏，然后「顺手修好」它。

## 4. 第 12 章 评测（读了原文，这章对本项目价值最高）

### 4.1 BFCL 有个 `irrelevance` 类别——**我们的 C2 有公认先例**

BFCL（Berkeley Function Calling Leaderboard，UC Berkeley，1120+ 样本）分四类：
`simple` / `multiple` / `parallel` / **`irrelevance`**。原文对 irrelevance 的描述是
「**判断是否真的需要调用工具**」。

**这和本项目 C2「口径未定义时拒答」结构完全同型。** 意义有两层：

1. **不是我拍脑袋发明的类别。** 「该不做的时候不做」是主流基准里公认的一个维度，
   写进简历/面试时可以引 BFCL 作为先例。
2. BFCL 用 **AST 匹配算法**评判函数调用，不是字符串比对。
   本项目的 C2 判定用 `RefusalCode` 枚举精确比对，属于同一思路的更强形式
   （拒答理由码是封闭枚举，比 AST 还硬）。

### 4.2 三种评估方法的分工，以及为什么本项目只该借一种

| 方法 | 它的用途 | 本项目该不该用 |
|---|---|---|
| **LLM Judge** | 多维度**绝对**评分（正确性/清晰度/难度匹配），快、一致、能给理由 | **不用。** 用 LLM 判断 LLM 有没有选对口径是**循环论证**——判官和被告共享同一套先验。本项目的机械判定（`metric_id` 精确匹配 + `RefusalCode` 比对）在 C1/C2 上**严格强于** LLM Judge |
| **Win Rate** | **相对**成对比较，让 LLM 判断 A 和 B 哪个好 | **借它的校准思想。** 原文：「理想情况下若生成题目质量接近真题，Win Rate 应在 **50% 左右**」——用一个**已知应当持平的对照**来校准评估器本身 |
| **人工验证** | 专家验证准确性，Gradio Web 界面降低门槛 | **本项目的 H2 复核实验就是这个**，且要求更严（限时 5 分钟、一致率 ≥ 80%） |

**Win Rate 的校准思想怎么用在 H2 上**：H2 现在只测「复核者看证据链的一致率 ≥ 80%」，
但**没有对照组**——80% 到底是高是低无从判断。可以加一组：让另一批复核者
**直接看年报原文**做同样的判断。若两组一致率相近，说明证据链承载了等价的信息；
若证据链组明显更低，差距就是证据链丢失的信息量。这比一个孤零零的 80% 有说服力得多。
（这条应记进 U-01 / Phase 2 的实验设计）

### 4.3 评测成本：我们的 §6 指标表缺了一整类

原文点破：「**评估成本的高昂，每次评估都需要大量的 API 调用，成本可能达到数百元甚至更多。**」
并给了 **渐进式评估** 的做法：先跑 5 个样本，`overall_accuracy > 0.8` 才扩到 50 个。

本项目 `EVAL_CASES.md` §6 有 7 个指标（口径正确率 / 拒答准确率 / 答案正确率 /
证据链完整率 / 复核一致率 / 引用可定位率 / 归因覆盖率）——**全是质量维度，
一个效率或成本维度都没有**。原文列的四类指标里，「效率指标（Response Time、Token Usage）」
我们整类缺失。

对一个求职项目，「这套评测跑一次多少钱、多长时间」是面试官会问的问题。
建议 §6 增补 **单次全量评测的 token 消耗与耗时**，并采用渐进式评估控制成本。
（已记入台账）

### 4.4 它自己承认的局限，正好是我们的反面教材

原文 §12.2.6 承认：`SimpleAgent` 用自定义的 `[TOOL_CALL:tool_name:parameters]` 格式，
「**这种格式需要 LLM 主动学习和使用**，在复杂场景下的表现可能不如原生 Function Calling」。

**「需要 LLM 主动学习和使用」——这正是本项目绝不能接受的。**
一个需要 LLM 配合才生效的口径闸门不是闸门。这句话是「万物皆 Tool」路线的必然结果，
也是我们选择前置钩子（见 `deepseek-harness.md` §5.1 单调守卫）的直接反证。
