## 1. Ch8 RAG：「按条分块保留条号」的三个坑

原文做法两段式：`_split_paragraphs_with_headings` 按 Markdown 标题栈切段，每段带
`heading_path`（如 `"第一章 > 第一节"`）和字符区间；`_chunk_paragraphs` 再按 token 合并。
思路对，实现有三个对审计致命的问题：

**坑 1：合并 chunk 时条号「最后一个赢」。**
`heading_path = next((x["heading_path"] for x in reversed(cur) if x.get("heading_path")), None)`
—— 跨越第 5 条和第 6 条的 chunk 只会被标成第 6 条。**这不是精度损失，是引用错标，而且无声。**

**坑 2：overlap 把上一 chunk 尾部带进下一 chunk，条号再按「最后一个赢」重算。**
第 5 条的原文可能出现在标着第 7 条的 chunk 里。**overlap 对语义连续有益，对条号可追溯是污染源。**

**坑 3：`heading_path` 依赖源文是 Markdown 标题。** 会计准则 PDF 里的「第十二条」是正文行内文本，
转换器不会把它变成 `#` 标题 —— 标题分块最多给到章/节，**拿不到条**。

**finaudit 的做法**：让「条」成为**原子单元，绝不跨条合并**，宁可 chunk 大小不均。
若确需合并，元数据存 `source_spans: [(条号, start, end), ...]` **列表而非单值**。
**准则库里 overlap 直接关掉。** 自己写 `第[〇一二三四五六七八九十百]+条` 正则切分器。

### 页码：原文完全没处理，这是硬缺口

`start/end` 是**转换后 Markdown 的字符偏移**，不是 PDF 页码。统一转 Markdown 的那一刻页边界就没了。
143 页年报的证据链要求「翻到第 87 页核对」，这条路径原文没给。
**finaudit 必须在转换前/中就固定 `(doc_id, page, bbox_or_charspan)` 三元组。**

### 命名空间隔离——可以直接抄

`where = {"memory_type":"rag_chunk", "is_rag_data":True, "rag_namespace":...}`：
即使共用一个 collection 也用 namespace + 元数据物理隔开。
**finaudit 应把准则库与年报库放不同 namespace，并在检索层强制：
问准则的检索永远不能命中年报正文，反之亦然。** 成本几乎为零，挡掉一整类串味错误。

### HyDE 必须排除，MQE 默认关闭——理由比「怕幻觉」更硬

**HyDE**（先让 LLM 写一段可能的答案性段落再拿它去检索）：在一个以「口径未定义必须拒答」
为核心主张的系统里，**检索链路第一步就是编造一段看起来很像答案的话** —— 这是结构化的确认偏误。
且它把一次 LLM 调用塞进检索路径：**同一问题两次运行得到不同假设文档、不同候选池、不同证据链。
证据链不可复现，审计就不成立。**

**更隐蔽的问题**：合并逻辑按 `max(score)` 去重再全局排序，但不同查询产生的相似度分数
**不在同一标定尺度上**。如果 finaudit 打算用「最高分低于阈值 → 证据不足 → 拒答」，
一旦开启 MQE/HyDE，**这个阈值就失去可解释性** —— HyDE 的假文档天然与文档库分布更接近，
分数系统性偏高，**会把本该拒答的问题推过闸门**。
→ **为了让拒答闸门可辩护，用单查询检索 + 标定过的阈值。**

### 嵌入兜底链：静默降级，必须改成大声失败

原文兜底是 百炼 API → 本地 MiniLM → TF-IDF，且维度不符时补零/截断、
单批失败时**写入零向量**只 print 一条 WARNING、最终报告「索引成功」。
→ 某几条准则被索引成零向量永远检索不到，系统却认为知识库完整，
**于是拒答变成了「检索不到所以说没规定」，理由完全错误。**
**索引构建必须事务性：任一 chunk 嵌入失败则整批失败并退出；
嵌入模型 id + 版本 + 维度写入索引元数据，查询时校验不一致就拒绝服务。**

### 检索评估：本章一个字都没有

没有召回率/精确率、没有标注集、没有消融实验。8.4.3 的「提升召回率 30%-50%」是
**无出处、无实验的断言**。**这一章借鉴不到任何检索评估，finaudit 必须自建。**
最小可行：为 20 个指标各备若干「应命中条号」的标注问题，测 recall@k 与
**条号精确匹配率**（正好能测出坑 1/坑 2）。

### token 估算两处实现互不一致

Ch8 的 `_approx_token_len` 与 Ch9 的 `_count_tokens` 算法不同。
控制分块大小用近似值可以，**用作上下文预算硬闸门不行**。finaudit 用一个真 tokenizer，一处定义。

## 2. Ch9 上下文工程

### 三条概念可直接写进设计文档

- **上下文腐蚀 / 注意力预算**：「上下文必须被视作一种有限资源，且具有边际收益递减」。
  机制解释是 n² 注意力被拉薄、训练分布中长序列稀少、位置编码插值牺牲精度，
  且是**性能梯度而非悬崖式崩溃** —— 所以问题不会以明显故障暴露，只表现为准确率缓慢下滑。
  **对审计场景，这种「看不出来的退化」比崩溃更危险。**
- **JIT 上下文**：不预加载全部，只维护轻量引用，运行时按需拉取。
  **这对年报比向量 RAG 更合适** —— 年报问题的检索目标通常是**已知位置**
  （合并资产负债表 / 附注五(12)），不是模糊语义匹配。
  finaudit 应建「章节-页码-科目」索引（一次性、确定性、可复核），
  提供 `read_pages(doc_id, from, to)` 与 `find_in_doc(doc_id, regex)`。
  **向量检索留给准则库这种真需要语义匹配的场景。**
- **混合策略**：前置 = 本次问题涉及指标的口径定义 + 报表结构页码索引；
  按需 = 附注、管理层讨论、比较期数据。

### 工具沙箱三层——形状可照搬

命令白名单（只读集）+ 工作目录沙箱（禁 `..` 逃逸与绝对路径越界）+ 超时与输出截断。
**但要改一处：输出截断必须可见。** 任何被截断的证据文本，其**截断事实和截断位置
必须进入证据链**，否则可能出现「引用指向了模型根本没看到的那一段」。

### 长时程三策略的取舍

- **Compaction**：「先优化召回，再优化精确度」。可用，加一条铁律：
  **压缩可以丢弃证据正文，绝不能丢弃引用 id。** 压缩后 `[E7] 准则第十二条` 必须还在。
- **结构化笔记（Markdown + YAML front-matter）**：note_type 分
  `task_state / conclusion / blocker / action`。
  **这个形状正好套得上「拒答是第一类产物」** —— 一次拒答 = 一条持久化的、带类型和 tag 的、
  人类审阅者能直接打开和批注的记录（`blocker` 几乎完全对应「口径未定义，阻塞」）。
  **拒答台账用 Markdown+YAML 存在仓库里跟着 Git 走，比塞进数据库更符合「可独立复核」。**
- **子代理**：对 finaudit 有**特定风险** —— 摘要是引用丢失的高发地。
  若使用，子代理返回值必须是**结构化 schema（含 citations 数组）**，不能是散文摘要。

### ContextBuilder：骨架该抄，实现基本不该抄

**该抄的固定分区骨架**：`[Role & Policies] [Task] [State] [Evidence] [Context] [Output]`。
把**证据与对话历史/记忆物理分开**，是「回答只能引用 [Evidence] 中的内容」这条约束
能够被表述、被检查的前提。

**不该抄的，逐条**：

1. **`_structure` 把证据的来源信息全部丢弃** —— `"\n---\n".join(evidence)` 只拼正文，
   heading_path、score、来源统统没渲染进上下文。
   **模型看到的证据没有任何标识符，因此它根本没有能力正确引用。**
   → finaudit 必须渲染成 `[E1] 来源=企业会计准则第14号 条号=第十二条 页=87 置信=0.83` 后接正文，
   并在 `[Output]` 里要求答案逐句标 `[E1]`
2. **`_select` 让证据和闲聊在同一个池子里按分数抢预算** —— 一条高分的最近对话可以把准则条文挤出去。
   **`[Evidence]` 必须有独立的、保留的 token 预算**
3. **`_calculate_relevance` 在中文上基本失效** —— `set(content.lower().split())` 的 Jaccard，
   中文没空格，一整句是**一个 token**，交集几乎恒为 0，叠加 `min_relevance` 会**静默丢弃中文 packet**
4. **`_calculate_recency` 对准则和年报有害** —— 2006 年的准则条文不比昨天的对话更不相关。
   注意 `ContextConfig.__post_init__` 断言权重和为 1.0，**需要绕过断言本身就说明这个抽象对本领域是错的**
5. **`_compress` 会静默丢掉后续所有分区** —— 遇到第一个装不下的 section 就截断并 `break`。
   由于 `[Output]` 放在最后，**压缩可以把输出格式要求整个删掉**。
   → finaudit 的压缩必须结构感知：每个分区有最低保留量，**证据以整条为单位丢弃**并记录被丢弃的 id
6. `_truncate_text` 两端都是近似，别用它切证据

## 3. Ch4：ReAct 循环**没有拒答出口**

原文 `run()` 只有两个出口：`Finish[...]`，或耗尽 `max_steps` 后
`print("已达到最大步数") ; return None`。**第二个出口返回裸 None，
没有理由、没有诊断、调用方无法区分「失败」和「答案就是空」。**

**finaudit 必须补的结构性缺口**：`Refuse[reason, missing_definition]` 要同时是
(a) 提示词里合法的 Action、(b) 循环里的一等终止状态、(c) 步数耗尽时的默认返回。
**拒答不能是「没能 Finish」的副产品，必须是主动可选的一步。**

原文自己的运行样例恰好演示了缺这一步的后果：搜索返回的是营销/论坛口水文，
Agent 照单全收，第二步就 Finish 了一个自相矛盾的答案。
**它没有「证据质量不足」这个概念，只有「信息够不够我写出一段话」。**

其他坑：正则解析散文（`re.match(...).group(1)` **没有 None 检查**，格式偏差直接抛异常）；
`history` 是 `list[str]` 把 Observation 全文追加**每步重发**（年报证据一进 Observation
几步就爆且反复计费）。
→ **用原生 function calling / JSON schema**（这也是原文 7.4.5 自己的结论）；
**history 只存证据引用 id + 一行摘要，全文留在上下文外**。

### Reflection 用于「自查引用」：只能占一半

**判断：Reflection 不适合承担引用校验本身，适合承担「拿到校验报告后修订或转拒答」。**

理由：原文成功的案例里评审员判断的是**它自己就能算出来的属性**（时间复杂度）。
而「引用是否正确」不是判断题是**查证题** —— 条号 X 是否存在？原文是否真的支持这句结论？
这两个问题有确定性答案，应由**确定性校验器**回答。
**让 LLM 校验引用，等于用一个会幻觉的部件去检查幻觉。**

三个失败模式都在原文样例里可见：
1. **终止条件是自评** —— 第二轮反思既提改进又宣布「无需改进」。
   **finaudit 的终止条件必须是：校验器返回零违规，或达上限 → 转拒答**
2. **评审员越权改写** —— 第一轮「反思」输出里直接包含了改进后的完整代码，评审员变成了作者。
   **必须用 schema 约束 reflector 输出为 `{verdict, violations[], missing_definitions[]}`，
   不允许输出答案正文**
3. **成本** —— 每轮至少两次额外调用。finaudit 这笔交易划算，
   但要**固定为一轮 verify-then-revise**，不要开放式循环

**正面可借鉴**：Reflection 的轨迹（`get_trajectory()` 把 execution/reflection 交替序列化）
**本身就是审计材料**。finaudit 应把「初稿 → 校验报告 → 修订稿」的完整轨迹持久化进证据链。

## 4. Ch7：与「闸门不可绕过」的六个冲突

**冲突 1（最严重）：`run(...) -> str` 是全局契约，没有地方承载结构化结果。**
Agent 返回 str，Tool 也返回 str。RAGTool 返回格式化字符串，Ch9 的 ContextBuilder 再
`_parse_rag_results` **反解**回 packet。**序列化→反解析这一来一回，正是引用元数据消失的地方**
（直接导致了 §2 的第 1 条）。
→ finaudit 必须定义
`AnswerResult { verdict: answer|refusal, answer?, refusal_reason?, definition_id, evidence: Citation[], warnings[] }`
作为统一返回类型。**这是与本框架最根本的不兼容，不要试图在 str 上叠 convention。**

**冲突 2：「一切皆为 Tools」在构造上就让闸门变成可选。**
7.1.2 原话「除了核心的 Agent 类，一切皆为 Tools」，而工具**是否被调用完全取决于 LLM 的选择**，
依据只是 `get_tools_description()` 拼进提示词的一行描述。
**把口径闸门实现为 Tool，它就永远只是建议。**
→ 口径解析必须在 `run()` 里、**在进入 LLM 循环之前**执行：
解析失败直接返回 refusal，**LLM 连一次都不被调用**。不要注册进 ToolRegistry。

**冲突 3**：`register_tool` 重名时**是 print 不是 raise**，然后照常覆盖。
**冲突 4**：`_tools` 与 `_functions` 两个注册表共用命名空间且互不检查；
函数注册的工具**没有 schema，只能靠提示词约束** —— 同一 Agent 里混着两种强度的执行保障。
**冲突 5**：`Message.to_dict()` **丢弃 metadata 和 timestamp**。
框架预留了 `metadata` 却没接线 —— **引用要在对话中存活，必须同时（a）渲染进 content 文本、
（b）存在以轮次为键的旁路存储里**。
**冲突 6：没有运行清单（run manifest）。** Config 和 Message 都不记录
「这个答案是哪个模型、哪个温度、哪个提示词版本、哪个索引快照产出的」。

**正面**：`ToolParameter` + `to_openai_schema()` 是正确的接缝。
两个小雷：`default` 被折进 description 文本；array 类型硬编码 `items:{"type":"string"}`
—— finaudit 若传科目代码列表会被静默当成字符串数组。

## 5. Ch10 MCP：现阶段是过度设计

**当且仅当满足以下之一才引入**：(a) 把 finaudit 自己做成 MCP server 供审计人员从
Claude Desktop 驱动（分发决策，可晚做）；(b) 需要消费一个大厂维护、你本来就要写适配器的外部源。

不引入的理由全部来自本章自身：
- 价值主张（免写 N 个适配器）在 **N=1~2 时不成立**
- **`MCPTool` 的自动展开与 Ch9 的建议直接矛盾** —— 一个 MCPTool 把服务器全部工具展开
  （文件系统服务器 → 14 个 `fs_*`），而 Ch9 明说「**如果人类工程师都说不准用哪个工具，
  别指望智能体做得更好**」并主张最小可行工具集
- **静默类型转换是缺陷** —— 原文明写「Agent 生成 a=25（字符串），系统自动转换为 25.0」。
  在财务取数层，`25` / `"25"` / `25.0` 的区别在金额、期间、科目代码上都是实质性的
- 远程传输支持有限，「建议直接使用底层 MCPClient」——还是得自己写
- **证据链角度**：任何进入证据路径的第三方 MCP server 都是**未版本化、未审计的依赖**

**A2A / ANP 用不上。** ANP 原文自承「还没有成熟的生态」，书里是自研的概念模拟。

## 6. Ch6 的选型轴：「涌现式协作」vs「显式控制」

finaudit 明确站在**显式控制**这边，而四个框架里只有 **LangGraph** 在这一侧。
原文对它的评价可直接用作选型依据：图结构带来「高度的可控性与可预测性……
对于构建需要高可靠性和**可审计性**的生产级应用至关重要」；原生支持循环，
「反思-修正」回路实现直接；每个节点是独立 Python 函数，
**插入一个「等待人类审核」的节点非常自然**（human-in-the-loop）。
它列的代价（更多前期样板、要思考「如何控制流程」）**恰好是 finaudit 应该付的成本**。

**反面**：AutoGen 被原文自己点名的失败模式是「对话式调试」——
出问题时「我们得到的不是清晰的错误堆栈，而是一长串的对话历史」。
**对需要复核的系统这是决定性的否决理由。**

**Ch5 唯一可用结论**：「用低代码平台快速验证想法，用代码实现精细化控制」。
