# Phase 1.5: 数据接入层 data-ingestion - Research

**Researched:** 2026-08-19
**Domain:** 年报 PDF 数值抽取的执行层设计（不重复研究抽取本身，只研究"抽出来之后怎么落地"）
**Confidence:** MEDIUM — 四个核心问题里，Q1（数值执行层）与 Q3 的接口形状部分是 HIGH（源码读出的事实）；
Q2（映射表形式）、Q3 的阈值、Q4 的字段集边界是设计选项列举，不是结论，故整体降级为 MEDIUM。

## Summary

本阶段的四个"尚未裁决问题"里，最关键的发现是：**`formula` 字段从未被 `src/semantic_layer/` 的任何模块解析为表达式**——它只在 `validate.py:59-61` 被当作普通字符串做 `field_id in formula` 子串包含检查，且这条检查只服务于 R2（符号约定是否必填），不检验语法。受限布尔 DSL（`dsl.py`）的词法器（`_tokenize`，34-237 行）没有任何分支处理 `+ - * /`，遇到这些字符会直接落进兜底分支 `raise DslError(...)`（236 行），报错文案本身就写着"算术运算...不在白名单内"。这意味着：**给 `formula` 建一个能执行的算术解析器，只要不去改 `dsl.py` 本体、不去改 `metrics/*.yaml` 的既有字段，就不会碰到 OpenSpec 的 9 条 Requirement 中的任何一条**——因为没有一条 Requirement 提到 `formula` 的语法约束，`formula` 唯一被规则触及的地方就是那个子串检查，而子串检查不关心 `formula` 内部是不是合法表达式。这是本阶段范围最大的一处"看起来危险、实际不冲突"的误判来源，值得在 Q1 里详细展开。

第二个关键发现：Q2（报表行项目 → 字段 id 映射表）与 Q3（AKShare 交叉校验）在结构上是**同一个问题**——两者都需要"外部标签字符串 → `metrics/*.yaml` 里已声明的 `source_fields[].id`"这条映射关系，区别只在于标签的来源（PDF 抽出的行标签 vs AKShare 返回的列名）。本仓库已经有一个可参考的架构先例：`metrics/_flags.yaml` + `vocabulary.py` 的"全局受控词表 + fail-closed 加载器"模式（缺任一必需键即拒绝加载，不补默认值）。这个先例本身没有被 CONTEXT.md 列为待裁决问题，可以作为形式选项之一提出。

第三个发现：`source_disagreement` 这个 flag **已经**在 2026-08-16 写进 `metrics/_flags.yaml`（`scope: system`，无 `trigger` 字段——这是 `system` 域 flag 的通例，触发逻辑只能活在运行时代码里，不能写进任何 YAML）。但仓库里目前**没有任何代码**会真正置位它——`resolve.py` 的 `active_flags()` 只遍历 `defn.flags`（即定义文件里声明的 `definition` 域标记），`system` 域标记的先例只有 `check_comparable()` 处理 `basis_version_mismatch` / `metric_version_mismatch` 这一个函数。`source_disagreement` 没有对应函数，Phase 1.5 要新建一个结构上类似 `check_comparable()` 的独立函数，而不是塞进 `active_flags()`。

**Primary recommendation：** 优先把 Q1（数值执行层）的架构决策做实——它是唯一一个"选错会牵连 20 份冻结定义或 9 条 Requirement"的高风险项；Q2/Q3 的映射表可以共用同一套"受控词表 + 版本化 + fail-closed"骨架（源不同、文件不同，机制相同）；Q4 只锁 SC-4/D-3 已经写死的字段，不多加一个字段，把"要不要现在顺手多存点"留给 planner 或操作者显式决定。

### Q1 — 数值执行层怎么建，才不动 Phase 1 的冻结契约

**`formula` 目前的真实写法（3 份定义原文，逐字取自本仓库）：**

| 指标 | `formula` 原文 | 来源 |
|---|---|---|
| `return_on_total_assets` | `is.net_profit / bs.total_assets` | `metrics/return_on_total_assets.yaml:35-36` |
| `current_ratio` | `bs.total_current_assets / bs.total_current_liabilities_period_end` | `metrics/current_ratio.yaml:34-35` |
| `accounts_receivable_turnover_days` | `365 * bs.accounts_receivable / is.operating_revenue_current` | `metrics/accounts_receivable_turnover_days.yaml:29-30` |
| `interest_bearing_debt_ratio` | `(bs.short_term_borrowings + bs.trading_financial_liabilities + bs.non_current_liabilities_due_within_one_year + bs.long_term_borrowings + bs.bonds_payable + bs.lease_liabilities) / bs.total_assets` | `metrics/interest_bearing_debt_ratio.yaml:66-73` |

这四份样本已经暴露 `formula` 的真实语法边界：字段引用（点号路径）、四则运算符 `+ - * /`、括号分组、数值字面量（`365`）。**没有一份使用比较运算符、逻辑运算符或 `is_missing()`**——这套语法与 `dsl.py` 的条件语法完全不相交（条件语法故意不含算术；`formula` 目前观测到的样本里也没有布尔构造），两者是互补而非重叠的两套 DSL。

**`formula` 能否被机械解析——现状是"完全不能"，且不是因为字段缺失，是因为语法冲突：**

`src/semantic_layer/dsl.py` 的 `_tokenize()`（160-237 行）只识别 `(` `)`、比较运算符、字符串、数字（含负数字面量）、标识符/字段引用；对 `+` `*` `/` 三个字符没有任何分支处理，会直接落进最后一行：

```python
# dsl.py:236
raise DslError(f"位置 {i}：非法字符 {ch!r}（算术运算与其他符号不在白名单内）")
```

`definition.py:197` 加载 `formula` 时只做 `formula=raw.get("formula")`——原样存成字符串，从不调用 `dsl.parse_condition()`。`validate.py` 里唯一触碰 `formula` 的地方是：

```python
# validate.py:59-61
def _formula_mentions(formula: str | None, field_id: str) -> bool:
    """字段是否参与公式运算。公式里出现即视为参与加减。"""
    return bool(formula) and field_id in formula
```

这是一次**子串包含检查**（`field_id in formula`），被 121 行的 R2（符号约定必填规则）调用，用来判断某个 `source_fields` 条目是否"参与公式"——它检验的是"这个字符串里有没有出现这个子串"，不检验 `formula` 是不是合法表达式。`[VERIFIED: src/semantic_layer/dsl.py:160-237, validate.py:59-61,121]`

**结论：`formula` 目前无法被机械求值出数值，但也没有任何现有代码依赖它"不能被求值"这一事实。** 这条空白是可以安全填补的，不是需要绕开的地雷。

**扩展会不会破坏 9 条 Requirement / 已枚举的规则码——逐条判断：**

先做一次事实校正：额外上下文提到"21 个规则码"，实际读 `validate.py` 枚举出的规则码是 **25 个**（`R0.YAML_UNPARSEABLE`、`R1.MISSING_GRAIN`、`R1.BAD_PERIOD_TYPE`、`R2.NO_SIGN_CONVENTION`、`R2.BAD_SIGN_CONVENTION`、`R3.DERIVATION_MISSING`、`R3.DERIVATION_NOTE_EMPTY`、`R3.DERIVATION_NOT_BOOLEAN`、`R4.FLAGS_KEY_MISSING`、`R4.FLAG_NOT_IN_VOCABULARY`、`R4.SYSTEM_SCOPE_FLAG_DECLARED`、`R4.TRIGGER_UNDECLARED_FIELD`、`R4.TRIGGER_UNPARSEABLE`、`R5.BASIS_FIELD_EMPTY`、`R5.BASIS_NOT_STRUCTURED`、`R6.ENUM_WITHOUT_VALUES`、`R6.NO_MISSING_REPRESENTATION`、`R7.EXPR_UNPARSEABLE`、`R7.NO_UNDEFINED_CONDITIONS`、`R7.REASON_EMPTY`、`R8.BOTH_ENFORCED_AND_ADVISORY`、`R8.ENFORCED_BY_UNRESOLVED`、`R8.PITFALL_UNBACKED`、`R8.TOO_FEW_PITFALLS`、`R9.VERSION_NOT_INT`、`R9.VERSION_TOO_LOW`）。`[VERIFIED: src/semantic_layer/validate.py 全文 grep 结果，本会话执行]`

| 规则组 | 是否涉及 `formula` 语法 | 新增计算层是否有触碰风险 |
|---|---|---|
| R0（YAML 合法性） | 否 | 无风险——计算层读的是已通过 R0 的 `formula` 字符串 |
| R1（`grain`/`period_semantics`） | 否 | 无风险 |
| R2（符号约定） | 是，但只做子串检查（`_formula_mentions`），不解析语法 | **唯一需要小心的点**：如果计算层要求把 `formula` 改写成新格式（例如换成结构化 AST 而不是字符串），会让 `field_id in formula` 这个子串检查失效，从而破坏 R2。**只要 `formula` 仍然是一个包含字段 id 文本的字符串（哪怕新增一个平行字段承载可执行形式），R2 就不受影响** |
| R3（derivation） | 否 | 无风险 |
| R4（flags 词表与触发条件语法） | 否——R4 管的是 `flags[].trigger`，与 `formula` 是两个不同字段 | 无风险，只要新计算层不复用/不修改 `dsl.parse_condition` 这条路径服务 `flags` 与 `undefined_conditions` |
| R5（`standard_basis`） | 否 | 无风险 |
| R6（枚举与缺失表示） | 否 | 无风险 |
| R7（`undefined_conditions` 语法） | 否——与 R4 同理，管的是条件表达式而非 `formula` | 无风险，同上前提 |
| R8（`common_pitfalls` 承载） | 否 | 无风险 |
| R9（版本号） | 否 | 无风险 |

**结论：25 条规则码里只有 R2 的两条（`R2.NO_SIGN_CONVENTION` / `R2.BAD_SIGN_CONVENTION`）与 `formula` 有关，而且只做子串匹配。只要新增的计算层不改写 `formula` 字段本身的字符串内容、不去修改 `dsl.py` 用于 `flags`/`undefined_conditions` 的语法（那条语法明文禁止算术，spec 原文："两者共用一套语法，MUST NOT 各自扩展"——`openspec/specs/semantic-layer/metric-definition/spec.md:140`），扩展在契约层面是安全的。**

**三个选项（不选，只列代价）：**

- **选项 A——在 `dsl.py` 之外新建一个独立的算术表达式解析器**（例如 `src/semantic_layer/formula.py` 或未来抽取器包下的一个模块），复用 `dsl.py` 里"字段引用词法"那部分逻辑的思路（点号路径识别），但语法上完全独立：支持 `+ - * / ( )` 与数值字面量，不支持比较/逻辑/`is_missing()`。
  - 代价：与 `dsl.py` 的词法器有一部分逻辑重复（字段引用识别、数字识别，约 30-40 行）；但换来的是零风险——不改 `dsl.py` 一个字节，`parse_condition`/`evaluate` 的语法边界（含 spec 明文的"不允许算术"约束）完全不受影响。
  - **本仓库有正面先例支持"重新手写一个专用解析器"这条路**：`dsl.py` 自己的 docstring（1-12 行）就写明了它没有用 Python 的 `ast` 模块的两个理由——① `is.` 前缀与 Python 关键字 `is` 冲突；② L3 的 `pre_execute` 要对语法树做静态检查，检查对象必须是"本模块自己定义的封闭节点集"。**这两条理由对 `formula` 解析器同样成立**：`formula` 里同样会出现 `is.xxx` 这种字段引用，用 Python `ast`/`eval` 直接解析会撞上同一个关键字冲突；而如果未来 `pre_execute` 也要对 `formula` 做静态分析（例如检查除零风险、检查字段是否都在 `source_fields` 里声明），拥有一个自定义、封闭的节点集同样重要。
- **选项 B——引入第三方安全表达式求值库**（例如 `simpleeval`，PyPI 首次发布 2014-05-28、26 个版本、MIT 协议，`[VERIFIED: PyPI JSON API 本会话查询]`；GitHub 仓库地址来自训练记忆，本会话未经工具确认，故标 `[ASSUMED]`）。
  - 代价：新增一个运行时依赖，需过 `scripts/verify_deps.py` 门禁（该门禁目前只做许可证禁列 + 哈希核验，MIT 协议不会被挡）；但引入外部依赖意味着放弃"封闭节点集"这个 L3 静态检查所需要的属性——第三方库的 AST 不是本项目定义的，`pre_execute` 若要检查它得反过来适配库的内部结构。这与选项 A 的核心权衡点相反。
- **选项 C（第三条路，按要求列出）——不解析 `formula` 字符串，改为给每个指标新增一个独立的、结构化的可执行表达式字段**（例如 `computation: {op: divide, numerator: [...], denominator: [...]}`）。
  - **这个选项与本阶段的一条明确非目标冲突**：CONTEXT.md §5「不动 `metrics/` 的 20 份定义（A-2 修在抽取层，**定义侧不动**）」。给每份定义新增一个字段，即便字段名不叫 `formula`，也是在改 20 份定义文件——这条路要走通，必须先由操作者放宽这条非目标，不能在计划里悄悄绕过。**如果操作者认为这条非目标只针对 A-2 那一件事、不针对"新增结构化计算字段"，需要显式澄清后再采用**，本研究不代替裁决。

三个选项中，A 与 B 都**不需要**触碰 `metrics/*.yaml`，可以在当前非目标下直接执行；C 需要先解除一条已写明的非目标。

### Q2 — "报表行项目 → 字段 id"映射表用什么形式

**本仓库已有的、结构类似的先例（可作为形式选项之一，不是唯一选项）：**

`metrics/_flags.yaml` + `src/semantic_layer/vocabulary.py` 是"全局受控词表"模式的现成范例：顶层一个 `vocabulary_version: 1` 整数字段做版本号；每个条目必须含 5 个必需键（`name`/`description`/`scope`/`affects_comparability`/`introduced_by`），加载器（`vocabulary.py:59-92`）对缺键 **fail-closed**——`ValueError` 直接拒绝加载，不补默认值。`[VERIFIED: src/semantic_layer/vocabulary.py:26,59-92; metrics/_flags.yaml 全文]` 该文件独立于 `metrics/*.yaml`（各指标定义只能引用，不能自造），这条"引用不能自造"的约束正是 SC-2 要求的"不允许模糊匹配"在词表场景下的既有实现方式。

`scan_rules.yaml` 的 `semantic_layer_provenance.allowed_field_prefixes`（`scan_rules.yaml:112-117`）是另一处相关先例：一个独立于 `metrics/` 的 YAML，枚举 `bs`/`is`/`cfs`/`notes`/`kpi` 五个受控前缀，与 `dsl.py` 的 `ROOT_NAMESPACES`（`dsl.py:66`）保持一致，`tests/test_conformance.py:102-118` 有断言校验两处不漂移。`[VERIFIED: scan_rules.yaml:112-117; src/semantic_layer/dsl.py:66]`

**如何避免"不允许模糊匹配"与"标签会跨行折行"这两条要求互相打架——这是本问题里最具体的设计张力，值得单独指出：**

CONTEXT.md §3.2 已实测的第 3 类失效模式（标签折行，数值行夹在两个标签片段之间，例如 `归属于母公司所有者权益` / 数值行 / `（或股东权益）合计`）意味着：**单个字段 id 对应的"标签"，物理上可能不是一整行连续文本，而是一个有序的文本片段序列**。如果映射表的 schema 只能表达"一个字段 id → 一个字符串"，作者要么被迫用子串/正则去容错折行（这就退化成模糊匹配，SC-2 明确禁止），要么每次遇到折行就手工拼接原文再存成一个大字符串（脆弱，报表格式一变就对不上）。**这条张力提示映射表的 schema 本身要把"标签 = 有序片段序列"当作一等构造**（例如 `label_fragments: [片段1, 片段2]`，要求按顺序、逐字匹配，中间允许且只允许"纯数值行"），而不是留给每个抽取器调用点各自发明拼接规则。这个设计要点是本研究从 A-6 的已实测事实（不重复研究该事实本身）推导出的映射表 schema 约束，供 planner 参考。

**cninfo 的反面教训，可直接作为"不允许模糊匹配"这条要求的正当性佐证（已读原文，非本会话重新实测）：**

`references/cninfo.md:204-213` 记录了一次真实实验：用子串匹配去对齐 AKShare 列名，产生了三处**看起来合理、实际取错**的映射（例如把"流动负债合计"的列错误映射到 `bs.total_liabilities`，把"净利润"错误映射到归母口径字段，把"应付票据及应付账款"合并列映射到本项目明文禁止合并的 `bs.accounts_payable`）。`[VERIFIED: references/cninfo.md:201-213（本会话 Read 工具原文核对）]` 这不是假设性风险，是已经在本项目的探测脚本里复现过一次的真实错误模式。

**与 `metrics/*.yaml` 的 `source_fields` 是什么关系——谁引用谁：**

`metrics/*.yaml` 的 `source_fields[].id` 是**已经存在、已冻结**的字段 id 全集（20 份定义共 30 个，CONTEXT.md §3.1 已用脚本核对过，本研究不重复验证）。这些定义文件同时携带 `statement`（报表名）与 `line_item`（人读的行项目描述，例如 `资产总计 —— 期末余额`），但这些是**给人看的文档字符串**，不是可执行的匹配规则——`definition.py` 加载它们时不做任何解析，只是原样存成 dataclass 字段。映射表要做的是给这同一组字段 id 提供**机器可执行**的版本：`{来源标签(可能是片段序列) → field_id}`。方向是单向的："映射表引用 `metrics/*.yaml` 已声明的 id 集合"（字段 id 的权威在 `metrics/`），而不是反过来。**两者存在潜在漂移风险**：如果映射表的标签描述与 `metrics/*.yaml` 里的 `line_item` 描述不一致（例如一个说"资产总计——期末余额"，另一个悄悄写成"资产总计——期初余额"），没有任何现有机制会报错——这类交叉一致性检查目前没有先例代码，需要 Phase 1.5 新增（可以参考 CONTEXT.md §3.1 提到的"用脚本从 `metrics/` 取出 30 个 `source_fields`"这个已实测动作，扩展成一条断言：映射表的 key 集合 == 30 个 `source_fields.id` 集合，不多不少）。

**两个形式选项（不选，列代价）：**

- **单一全局映射文件**（类比 `_flags.yaml`，例如 `data/mappings/statement_field_map.yaml`），`mapping_version` 整数版本号，一次性收录全部字段与各来源（PDF/AKShare）的标签变体。
  - 代价：当前只有一家公司一年年报，文件不大；但长期看，不同公司/不同事务所排版差异会让这个文件持续膨胀，变成单点冲突热点（多人协作时的合并冲突面），且"一个文件混杂 PDF 标签与 AKShare 列名"会让 Q2 与 Q3 的关注点耦合在同一份文件里。
- **按报表拆分的多文件**（对应 `is`/`bs`/`cfs`/`notes`/`kpi` 五个已有命名空间，例如 `bs.yaml`/`is.yaml`/...），与 `dsl.py` 的 `ROOT_NAMESPACES` 和 `scan_rules.yaml` 的 `allowed_field_prefixes` 天然对齐。
  - 代价：读者要在"某个字段属于哪张报表"和"该去哪个文件找它的映射"之间做一次心智跳转；好处是把失效面按报表边界天然切开，且与已有的五类前缀约定复用同一套心智模型，不需要新发明一套分类。

### Q3 — AKShare 交叉校验怎么做

**AKShare 取三大表的接口、字段名、口径披露程度（引自本仓库已有研究产物，非本会话重新实测；标注为该文档记录的实测结果）：**

`references/cninfo.md:201-202` 记录：`ak.stock_financial_report_sina(stock="sh600519", symbol="资产负债表")` → 资产负债表 103 期 × 147 列，利润表 103×83，现金流量表 99×71。`[VERIFIED: references/cninfo.md:201-202（本会话 Read 工具原文核对）]` 列名是**原始中文列名**（如"净利润""流动负债合计"），不携带口径说明——即"取的是含少数股东损益还是归母、是否含税、是否年化"等信息都不在列名里，需要人工逐列确认。这与 Q2 的结论完全同构：**AKShare 侧同样不能用子串匹配去对齐列名到 `field_id`**，`references/cninfo.md:204-213` 记录的三处子串匹配错误就是拿 AKShare 列名做的实验，已在 Q2 一节引用，不重复列出。**推论：Q2 的映射表机制应当推广为"按来源区分"的两组条目（PDF 标签 → field_id，AKShare 列名 → field_id），而不是分别建两套互不相关的机制**——这是本研究新增的设计建议，不在 CONTEXT.md 原文中，供 planner 判断是否采纳。

**"不一致"的判定阈值怎么定——本仓库任何权威文档都没有给出具体数字，如实标注为空白，不替补一个数字：**

`PROJECT_SPEC.md`、`DECISIONS.md`（含 D-013）、`metrics/_flags.yaml` 里 `source_disagreement` 的定义（"年报 PDF 抽取值与对照源（AKShare）不一致，该不一致本身作为证据记录"）均未给出容差数值、也未说明比较方式（绝对差 vs 相对差 vs 四舍五入位数）。`[ASSUMED — 以下是本研究基于领域常识列出的需要决策的具体维度，不是任何来源给出的结论]`

- **单位必须先于数值比较被消除**：PDF 抽取值单位固定为"元"（报表页头印字，CONTEXT.md §3.2 已实测），而 AKShare 的列是否同为"元"未经本会话验证——若两者单位不同（例如一个是元一个是万元），在做数值比较之前不先归一化，几乎 100% 的比较都会被判定为"不一致"，这会让 `source_disagreement` 变成噪音而非信号。这条不是"要不要设阈值"的问题，是"阈值判断的前置步骤"，建议 planner 把它当作一个独立任务点，不要与阈值选择混在一起讨论。
- **四舍五入 / 精度差**：PDF 原文通常精确到分（两位小数，CONTEXT.md §3.2 的数值正则要求 `^-?[\d,]+\.\d{2}$`），AKShare 聚合值的精度未经本会话验证，可能存在系统性舍入差。
- **绝对差 vs 相对差**：小额科目用绝对差容易误判，大额科目用相对差更合理，但具体切换点/容差比例本研究不下结论。

**`source_disagreement` 现有实现里怎么被置位——现状是"完全没有被置位"，需要新建：**

`metrics/_flags.yaml:73-77` 显示该 flag `scope: system`，且**不含 `trigger` 字段**——这与其余两个 `system` 域 flag（`basis_version_mismatch`、`metric_version_mismatch`）的写法一致，`[VERIFIED: metrics/_flags.yaml 全文（本会话 Read 工具核对，19-35 行 / 73-77 行）]`，符合 spec 的规定："scope 为 system 的标记由运行时产出，MUST NOT 在口径定义文件内声明"（`openspec/specs/semantic-layer/metric-definition/spec.md:54`）。也就是说 `_flags.yaml` 里**从来就不该出现**这个 flag 的触发逻辑——触发逻辑只能活在 Python 代码里。

现有运行时代码里，唯一处理 `system` 域 flag 判定的函数是 `resolve.check_comparable()`（`resolve.py:254-274`），它的输入是同一指标的两份 `MetricDefinition`（跨期比较场景），逻辑是按 `standard_basis` 的 `name` 配对比较 `version`。`resolve.active_flags()`（`resolve.py:221-246`）只遍历 `defn.flags`——即定义文件内声明的 `definition` 域标记列表，`system` 域标记按 R4 规定根本不会出现在这个列表里，所以 `active_flags()` 结构上**不负责**、也**不应该**被改造去处理 `source_disagreement`。`[VERIFIED: src/semantic_layer/resolve.py:221-274]`

**推论（架构建议，不是四个禁止裁决项之一，供 planner 参考）**：`source_disagreement` 的置位逻辑应当是一个与 `check_comparable()` 平行的独立函数（例如 `cross_validate(pdf_value, akshare_value, tolerance...) -> flag | None`），输入是单个字段的两个来源取值，而不是塞进 `active_flags()` 内部——这与 `check_comparable()` 已经确立的"system 域标记各自有独立判定函数"的架构惯例一致，也避免了在单期取数路径（`active_flags`）里混入需要访问第二个数据源的逻辑。

### Q4 — 证据链在本阶段要落到什么程度

**已锁定、不需要裁决的部分（直接引自 ROADMAP SC-4 与台账 D-3，原文摘录）：**

> 抽取产物带出处：PDF 的 SHA-256 + 巨潮源 URL + 页码 + 计量单位与币种（ROADMAP SC-4）
> 抽完就删 PDF，默认不保留；落库的是「结构化行 + PDF 的 SHA-256 + 巨潮源 URL + 页码」（台账 D-3）

这四／五个字段（SHA-256、源 URL、页码、单位、币种）**已经是决策**，不在"尚未裁决"之列，本研究不重新论证要不要它们，只研究"用什么形状承载它们，且不预先决定 U-01 的完整字段集"。

**U-01 明确的边界**：U-01 问的是"一次回答"的完整证据链字段集（供 AC-05/H2 复核实验使用），而 SC-4 问的是"一条被抽取的报表行"的出处记录——**两者粒度不同，SC-4 的记录是 U-01 未来可能引用的输入之一，不是 U-01 本身**。只要 Phase 1.5 只落地 SC-4 已经点名的字段、不额外发明新字段去揣测 U-01 会长成什么样，就不构成提前拍板。

**最小可行形状（把已锁定字段组织成一个结构，不新增字段）：**

按 SC-4 原文，每条被抽取的字段值至少需要携带：`field_id`（对应 Q2 映射表解出的字段 id）、`value`（抽出的值）、`pdf_sha256`、`source_url`、`page`（CONTEXT.md §3.2 已实测的失效模式 2 说明"页"不总是单一整数——合并表与母公司表可能在同一页内切分，折行标签可能横跨两页——所以 `page` 的类型选择本身就是一个需要 planner 明确的实现细节：单页码、页码区间、还是"标题锚点所在页 + 数值实际所在页"两个字段，本研究不替选，只指出这个字段不能想当然设成单一 int 而不考虑已实测的跨页事实）、`unit`、`currency`。这六项里，`field_id` 与 `value` 是显然必须的（否则记录无法回指是哪个数），其余四项是 SC-4/D-3 明文要求的。

**两条来自外部项目的、可直接复用的设计原则（已读原文，非本会话新调研，仅在此落地到 Phase 1.5 的具体粒度）：**

- **显式引用而非时间顺序推断**：`references/deepseek-harness-deep-read-part4.md` 记录 harness 的 `sourceEventSeqs` 是结果事件对来源事件的**显式**数组引用（"target 直接引用的更早事件"），而不是靠事件在日志里的先后顺序去推断关联。落到本阶段：如果 Phase 1.5 的数值执行层（Q1）要把"一个算出来的指标值"和"参与运算的若干条抽取记录"关联起来，这条关联也应当是显式的（例如计算结果携带一个字段值列表，每个引用它所依赖的具体 `field_id`+`page` 记录），不要依赖"同一次抽取批次""同一个文件写入顺序"这类隐式假设。
- **拒答/异常的结构化理由码，不要退化成自然语言**：同一份深读记录（引自 `docs/agent/OPEN-ITEMS.md` D-23，已读原文）指出 harness 把拒绝原因压平成一句自然语言字符串是一个反面案例。落到本阶段：如果某个字段抽取失败或勾稽校验不通过（SC-7），失败原因也应该是可机读的结构（类似 `resolve.py` 里 `RefusalCode` 这个封闭枚举的做法），而不是一句自由文本日志。这与 SC-7"阻断式"的要求是同一件事的两面——阻断本身不难，难的是阻断的原因要能被下游机器消费。

**什么留给以后（不在本阶段加）：** 抽取方法/置信度、匹配到的原始文本片段、抽取时间戳——这些对未来更完整的证据链有价值，但 SC-4 没有点名要求，本研究不建议现在就加（会构成事实上的 U-01 提前拍板）。是否现在顺手加、加了要不要写进 SC-4，属于需要操作者或 planner 显式决定的discretion，本研究只指出这是一个决策点，不代为决定。

## Common Pitfalls

### Pitfall 1：把 `formula` 解析器接进 `dsl.parse_condition()`
**What goes wrong：** 为了图省事，把算术运算加进 `dsl.py` 现有的 `_tokenize`/`_Parser`，让 `flags[].trigger`/`undefined_conditions[].expr` 也"顺便"能写算术。
**Why it happens：** 两套语法都要处理字段引用词法，代码看起来高度相似，容易想"合并省事"。
**How to avoid：** 严守 spec 原文"两者共用一套语法，MUST NOT 各自扩展"（`openspec/specs/semantic-layer/metric-definition/spec.md:140`）——这条约束保护的是 `flags`/`undefined_conditions`，不是 `formula`；`formula` 从来不在这套共享语法的管辖范围内，给 `formula` 单独开一条路完全合规，但如果代码层面复用了 `dsl.py` 的公开解析入口，就等于让 `flags`/`undefined_conditions` 也间接获得了算术能力，直接违反该条 Requirement。
**Warning signs：** 任何 PR 里出现 `dsl.py` 的 `_COMPARE_OPS`/`_tokenize` 附近新增 `+`/`-`/`*`/`/` 分支，都应视为红旗。

### Pitfall 2：把"命中数"当验收指标
**What goes wrong：** 用"30 个字段里抽到几个"衡量映射表/抽取器质量。
**Why it happens：** 命中数好统计、好写进报告。
**How to avoid：** ROADMAP SC-8 已经把这条写成成功标准（"验收看取到的值，不看命中数"），起因是 A-4 实测中 `bs.total_equity` 曾"命中"章节小标题而取值为空。本阶段任何验收动作都要看具体取到的值，不能只看命中/未命中的布尔值。
**Warning signs：** 验收报告只列"X/30 命中"这一个数字，没有逐字段展示实际抽出的值。

### Pitfall 3：跨源比较前不做单位归一化
**What goes wrong：** 直接比较 PDF 抽取值与 AKShare 值的数值大小，单位不一致（元 vs 万元）会让几乎全部比较都触发 `source_disagreement`，把这个 flag 变成噪音。
**Why it happens：** `unit_scale_mismatch` 是另一个独立的 flag，容易忘记它与 `source_disagreement` 的判定顺序有依赖关系。
**How to avoid：** 见 Q3 一节——先归一化单位，再判定数值是否"不一致"。

```python
# Source: src/semantic_layer/resolve.py:254-274（本仓库现有代码，本会话 Read 工具核对）
def check_comparable(a: MetricDefinition, b: MetricDefinition) -> Refusal | None:
    if a.metric_id != b.metric_id:
        raise ValueError(
            f"check_comparable 只用于同一指标的两期：收到 {a.metric_id!r} 与 {b.metric_id!r}"
        )
    if a.version != b.version:
        return Refusal(
            RefusalCode.CROSS_VERSION_COMPARISON,
            f"口径版本不同（{a.version} vs {b.version}）：版本变更即口径变更，历史结论不可跨版本比较。",
            metric_id=a.metric_id,
        )
    b_versions = {sb.name: sb.version for sb in b.standard_basis if sb.name}
    for sb in a.standard_basis:
        if sb.name in b_versions and b_versions[sb.name] != sb.version:
            return Refusal(
                RefusalCode.CROSS_BASIS_VERSION_COMPARISON,
                f"准则《{sb.name}》两期版本不同（{sb.version} vs {b_versions[sb.name]}）。",
                metric_id=a.metric_id,
            )
    return None
```
