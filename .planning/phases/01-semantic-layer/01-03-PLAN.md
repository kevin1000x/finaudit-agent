  <action>
    在 `scan_rules.yaml` 里定义全部规则，代码只做执行不做判断——规则要能被人审查，这是 D-010
    「扫描规则本身也进版本控制」的意思。文件顶层含 `rules_version: 1` 与四组规则：

    第一组 `forbidden_tracked_file_types`：被 git 跟踪的文件扩展名黑名单。Phase 1 取值为
    表格类、文档类、数据库类与年报原件类扩展名（`.xlsx` / `.xls` / `.csv` / `.db` / `.sqlite` /
    `.parquet` / `.pdf` / `.docx`）。理由：Phase 1 不需要任何数据文件进仓库，
    真要进也必须是显式决策而不是顺手 `git add`。判据用 `git ls-files` 的输出，不扫工作区未跟踪文件。

    第二组 `gitignore_required_entries`：`.gitignore` 中必须存在的隔离条目，取值为现有的
    `data/raw/`、`data/private/`、`data/cache/`、`.env`。缺任一条即 `GITIGNORE_COVERAGE_LOST`。
    这条防的是「有人为了跑通某个脚本临时删掉隔离规则然后忘了加回来」。

    第三组 `content_patterns`：正则模式 + 规则码 + 说明。Phase 1 收三类：
    企业邮箱域名形态（`CONTACT_PATTERN`）、私网与内网主机名形态（`NETWORK_PATTERN`）、
    以及一个初始为空的 `organization_tokens` 列表（`ORG_TOKEN`）——留空是有意的，
    它是**发现真实失效模式后**才往里加的位置，不预填猜测值。扫描范围限定在被 git 跟踪的文本文件，
    并含自排除规则：`scan_rules.yaml` 自身不参与 `content_patterns` 匹配（否则规则文件永远命中自己）。

    第四组 `semantic_layer_provenance`：这一组是本项目特有的，也是最有价值的一条。
    `allowed_statements` 列出由准则规定、可在任何一份公开年报里找到的报表与章节名称：
    合并资产负债表、合并利润表、合并现金流量表、合并所有者权益变动表、财务报表附注、
    主要会计数据和财务指标。`allowed_field_prefixes` 列出 `bs` / `is` / `cfs` / `notes` / `kpi`。
    扫描器对 `metrics/*.yaml` 的每个 `source_fields` 条目检查其 `statement` 属于前者、
    id 的第一段属于后者，否则分别报 `STATEMENT_NOT_PUBLIC` 与 `FIELD_PREFIX_UNKNOWN`。
    这就是把 CLAUDE.md 那句人工自查（这个字段名是从哪来的）变成机器提问：
    **来自公开披露报表的哪一张。答不上来就失败。**

    `scan.py` 实现 `ScanRules` / `ScanFinding` / `load_scan_rules` / `scan_repository`。
    行为按 fail-closed 设计：规则文件缺失或解析失败即视为扫描失败（非零退出），
    不允许「规则读不到就当通过」。`__main__.py` 追加 `scan` 子命令，
    支持 `--rules` 指定规则文件、`--json` 输出机读结果，有任一 Finding 时退出码 1。

    扫描结果排序必须稳定（按 path 再按 rule），否则 CI 与人工对比会产生噪音 diff。

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| 开发者输入 → git 仓库 | 手写内容可能携带非公开来源；这是 D-010 认定的唯一不可挽回错误的入口 |
| `scan_rules.yaml` → 扫描器 | 规则文件是扫描行为的唯一来源，篡改或缺失即等于关闭门禁 |
| `metrics/*.yaml` 字段名 → 公开性判定 | 字段名是最隐蔽的泄漏载体：一个内部系统的列名混进来，从内容上看不出异常 |

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
