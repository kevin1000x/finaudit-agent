### ⚠️ 一个真实的近音陷阱：`grep audit` 现在有二十多处命中，全都不是审计意见

仓库里现在有 `streaming_audit` / `audit_output_path` / `max_audit_reports` / `_enforce_streaming_audit_retention`。

ROADMAP 自己记着那次教训）。这次记的是它的反面：**关键词命中不等于能力存在。**

## §3 三周里新出现的事实（ROADMAP 里没有）

### 3.1 🔴 `data/` 实际是空的 —— Phase 0 的成本不在分析，在取数

```
data/dictionaries/cn_financial_sentiment.txt
data/dictionaries/NOTICE.md
data/dictionaries/source/中文金融情感词典_姜富伟等(2020).xlsx
data/parsed/.gitkeep
data/raw/.gitkeep
data/results/.gitkeep
```

**六个文件，三个是 `.gitkeep`。** 没有任何年报 PDF，没有任何中间产物，没有任何结果。

⇒ **「不写新代码」听起来很轻，但它掩盖了真正的工作量**：这个阶段的第一件事是
**建一个语料**，而语料要从巨潮一份一份下。ROADMAP 里那句「一条实证结论两三天就能出」
**是在没有量过取数成本的前提下写的**。

**唯一有的语料尺度锚点**是本仓自己的三份年报（`data/raw/`，已 gitignore）：

| 文件 | 页数 | 体积 |
|---|---:|---:|
| `600519_2023.pdf` | 143 | 3.4 MB |
| `600309_2019.pdf` | 213 | 3.7 MB |
| `002352_2021.pdf` | 282 | **24.4 MB** |

⚠️ **三份的体积差 7 倍**，中位 3.7 MB、均值 10.5 MB。**用均值估总量会高估，用中位会低估**，
两个都要写出来，不要只报一个。

### 3.2 🔴 MIT 声明 + 无条件 `import fitz`（AGPL v3），而仓库是 PUBLIC

**实测**（2026-09-02）：

- `LICENSE` 第 1 行 `MIT License`，第 3 行 `Copyright (c) 2024 [Your Name]`
  —— **版权行还是模板占位符**
- `src/pdf_parser.py:17` 是 `import fitz  # PyMuPDF`，**在模块顶层、无条件、不是可选依赖**
  ⇒ 没装 PyMuPDF 连 `import` 都过不去
- `requirements.txt` 里 `PyMuPDF>=1.23.0`
- `gh repo view` 实测：`visibility: PUBLIC`，`pushedAt: 2026-08-23`，2 stars，**description 为空**

**这正是本仓 `A-3` 查出、并因此立了 `D-014` 的那个形态**，只不过发生在另一个仓库、
且那个仓库是公开的。

⚠️ **我不做法律判断，只陈述事实。** 处置属于操作者，见 `A-13`。
⚠️ **Phase 0 会放大这件事**：这个阶段的产物就是把那个仓库的 README 变成一张对外的脸。

### 3.3 巨潮的全文检索支持关键词，而现在恒为空

`src/downloader.py` 的查询体里有 `'searchkey': ''` 与 `'stock': stock_param`。

⇒ 现在的用法是**按公司逐个查**，必须先有公司清单（`examples/company_list.csv`，
当前 **10 行**）。**按标题批量找**（见 §4.1 的抽样设计）需要改这个查询 —— 属新增能力，
落在 `A-12` 那条边界问题上。

### 3.4 环境是重的，且没有现成的 venv

`requirements.txt` 含 `tabula-py`（**要 Java 运行时**）、`camelot-py[cv]`（要 OpenCV）、
`pytesseract`（**要 Tesseract 二进制**）、`PyMuPDF`、`supabase`、`akshare==1.18.64`（**钉死版本**）。
仓库里**没有 `.venv` / `venv` 目录**。

⚠️ `akshare==1.18.64` 与本仓 `[crosscheck]` extra 的 `akshare>=1.18.94` **不是同一个版本**。
两个仓库各自独立装，**不要共用一个环境**。

### 3.5 验证码是已知故障模式

README 有一节「登录与验证码处理」，列了三套方案（手动 Cookies / Selenium / Playwright），
「故障排查」里也有「验证码拦截」一条。

🔴 **这条对本阶段是硬约束**：**agent 不绕验证码、不做 bot 检测规避**。
一旦触发，取数这一步必须由**操作者本人登录并导出 cookies**，agent 只能用给定的 cookies。
⇒ **取数不是一个可以放着跑的自动步骤**，规划时必须按「需要人在场」来排。

## §4 推荐方向的可行性：先算，再决定

ROADMAP 推荐 **年报可读性 Fog 指数 vs 非标审计意见**，并判定「方向成立，无需加数据源」。
**方向本身没有问题**（审计意见确实印在年报 PDF 里，措辞高度模板化）。
**但抽样设计有一个 ROADMAP 没算过的问题。**

### 4.1 🔴 非标审计意见是稀有事件，随机抽样在这里不成立

要拿到 `k` 个非标样本，随机抽 `n` 个公司年，`E[k] = n × p`：

| 非标基准率 p | k=10 | k=30 | k=50 |
|---|---:|---:|---:|
| 0.5% | n≈2,000 | n≈6,000 | n≈10,000 |
| 1.0% | n≈1,000 | n≈3,000 | n≈5,000 |
| 1.5% | n≈670 | n≈2,000 | n≈3,330 |
| 3.0% | n≈330 | n≈1,000 | n≈1,670 |

⚠️ **上表里的 `p` 全是假设值，不是实测。** A 股非标比例本阶段**没有量过**，
量它本身就是第一个任务（见 `00-01-PLAN`）。**在量出来之前，不要引用上表任何一行当结论。**

按 §3.1 的体积中位数 3.7 MB 估：`n=2,000` ≈ **7.4 GB**（按均值 10.5 MB 估则 ≈ 21 GB），
外加同等数量的下载请求 —— 而 §3.5 说取数可能需要人在场。

⇒ **随机抽样这条路，代价与「两三天出一条结论」不在一个量级。**

### 4.2 一条可能便宜得多的路（**未验证，不是结论**）

出具非标意见时，上市公司**另有强制披露义务**：董事会/监事会要就非标意见出
**专项说明**，那是一份**标题高度模板化的独立公告**。

⇒ 若巨潮的全文检索能按**公告标题关键词**批量返回，就能在**不解析任何 PDF** 的前提下
先框出候选公司年，再对候选做**病例—对照**抽样（非标组 + 同行业同规模的标准组）。

⚠️ **这一条今天没有验证任何一环**：
- 巨潮的 `searchkey` 参数**实际能不能按标题命中**，未测
- 那类公告的标题措辞**有几种变体**，未测
- 「有专项说明」与「审计意见非标」是不是一一对应，**未核**
- 病例—对照会引入**选择偏倚**，它在结论的「局限」一节里必须写出来（`AC-03` 要求含局限）

**⇒ 这是一个候选，不是一个方案。** 它要不要走，取决于 `00-01-PLAN` 量出来的东西。

### 4.3 无论走哪条，有一件事不变

**审计意见的抽取器必须先存在，且必须被验过。**
Fog 指数已经有了（§2 第 1 条），**缺的那一半始终是审计意见这一侧**，
这与 2026-08-10 那次更正的结论一致：**缺的不是数据，是抽取器。**

⚠️ 本仓 Phase 1.5 的教训在这里直接适用：
- 抽出来的值**必须逐条人工核对**才算「能抽出」（`SC-2` 的计数口径）
- **同值干扰项在人工核对里是免检的**（`N-48`）—— 审计意见是**分类变量**，
  这个陷阱在这里的形态是：**把「无保留」误判成「带强调事项段的无保留」，两者都会被读成「非非标」**
- 「代码里没有」不等于「数据里没有」（ROADMAP 自己记的 2026-08-10 教训）
