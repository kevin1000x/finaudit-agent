# ROADMAP — finaudit-agent

> 投入约束：**无时间预算上限**，实际投入以 `docs/agent/PROGRESS.md` changelog 记录（D-008，2026-08-10 修订）。
> 下方各阶段的工期估算是**规模参照**，不是承诺，也不再是排期依据。
> 设计原则：**每个阶段结束都是一个完整的故事**，不存在"做了一半"的项目叙述。

---

## Phase 0 — cninfo 实证结论（规模：小）

**目标**：不写新代码，只给 `cninfo-financial-analyzer` 补一条可复现的实证结论。

**为什么第一个做**：这是唯一能在 9 月投递期立刻变现的动作。语义层再好，9 月还没做完；而一条实证结论两三天就能出，且立刻让一个"工具"变成一个"研究"。

**交付**
- 一条实证结论（推荐方向：年报可读性 Fog 指数 vs 非标审计意见）
- 一张图 + 三行结论写进 README 首屏
- README 首屏改造：问题 → 方法一张图 → 结论 → 怎么跑

**阶段门**
- AC-03：结论可复现，含数据范围、方法、显著性、局限
- 结论中的每个数字都能用仓库里的命令重跑出来

**最小可讲成果**："我做了一个财报文本实证研究，发现年报可读性和审计意见有关。"

**明确不做**：不动 agent、不加新数据源、不重构 cninfo。

## Phase 1 — 语义层（9 月，6 h/周）

**目标**：20 个核心财务指标的机器可读口径定义。这是唯一别人抄不走的一层（D-002）。

**交付**
- `metrics/*.yaml`：每个指标含 `source_fields` / `formula` / `standard_basis` / `period_semantics` / ≥3 条 `common_pitfalls`
- 一个能机械消费这些定义的最小校验器（不是 Agent）
- 冻结的评测问题集 ≥ 20 题（C1–C5 五类），带时间戳与哈希
- 非公开数据自动扫描脚本

**阶段门**（见 `EVAL_CASES.md` §7）
- AC-01：20 个指标字段齐全
- C2 类拒答准确率 = 100%（**一个都不能猜**）
- 问题集已冻结
- AC-10：仓库零非公开数据

**最小可讲成果**："我把 20 个财务指标的口径固化成了机器可读的定义，因为我在审计和商分都被口径不一致坑过。"

**可对外**：本阶段结束时把 `metrics/` + 问题集单独开源为姊妹仓库（D-005）。

**明确不做**：不做 Agent、不做 TUI、不做 RAG。

## Phase 2 — TUI + 可信执行层（10–11 月，8 h/周）

**目标**：能跑通一次完整问答，并产出可复核的证据链。

**交付**
- TUI 骨架（问答 + 证据链侧栏），做到能展示即止（D-006）
- Hook 机制：`pre_execute` 口径与权限校验 + AST 静态检查；`post_execute` append-only trace
- 失败归因分层（检索/口径/计算/表达，允许多标签）
- **复核实验**：15 题、限时 5 分钟、只看证据链

**阶段门**
- AC-05：证据链完整率 100%
- **AC-06：复核一致率 ≥ 80%**（H2 判定门）
- 「无法判断」占比 ≤ 20%
- AC-08：归因覆盖率 100%

**若复核一致率 < 60%** → **停止，回到 ARCHITECT 重设计证据链，不得进入 Phase 3。**

**最小可讲成果**："我给分析 agent 加了执行钩子，每次回答都带证据链，而且我做了实验验证人能不能靠它复核。"

**明确不做**：不做主题美化、不做插件体系、不做快捷键。

## Phase 3 — 知识层（12 月–1 月，寒假密集）

**目标**：准则 RAG（引用可追溯）+ 条件性图谱。

**交付**
- 准则语料的分块策略（按条分块，保留条号）与年报分块策略（按 MD&A 段落，保留公司/年份/章节元数据）
- 引用可追溯：每条回答能指回「XX 准则第 X 条」或「XX 公司 20XX 年报 MD&A 第 N 段」
- **图谱前置检验**：先写出 3 个「纯向量 RAG 答不了、图能答」的问题并实证证明

**阶段门**
- AC-07：引用可定位率 ≥ 90%（抽检 20 条）
- C5 类给出实证对比，而不是论证

**若证明不了图的必要性** → **跳过图谱，记录理由**。这不是失败，是省下的工作量（D-007）。

**最小可讲成果**："我做了准则 RAG，每条回答能指回具体条号。"

---

## Phase 4 — 评测闭环与对外材料（2–3 月，6 h/周）

**目标**：把项目变成可展示的东西，并决定是否开源。

**交付**
- 完整评测报告：分层结果 + 失败归因分布
- 三样对外替代物（D-005）：一页架构图、60 秒 TUI 录屏、一页脱敏评测报告
- 开源决策（那时大概率已有 offer，风险最低）

**最小可讲成果**："我为它建了评测集，N 个问题对 M 个，错的分别错在检索层/口径层/计算层。"

## 依赖与顺序约束

```text
Phase 0  ──独立，可随时做
Phase 1  ──独立，不依赖 Phase 0
Phase 2  ──依赖 Phase 1（没有语义层，Hook 无从校验）
Phase 3  ──依赖 Phase 2 的 H2 判定门通过
Phase 4  ──依赖 Phase 2；Phase 3 可选
```

**Phase 0 与 Phase 1 可以并行。** 原先因 8 小时预算不建议并行，该约束已随 D-008 修订取消；
现在的判断依据是注意力而非小时数——两个阶段验证的东西不同（实证结论 vs 语义层），切换成本真实存在。

## 触发重估的条件

| 条件 | 动作 |
|---|---|
| 连续两周未推进 | 砍阶段目标，不加时（D-008） |
| 转正述职期 | 全面暂停 |
| 出现更好的开源替代 | 停止自建，转为使用并贡献（`PROJECT_SPEC.md` §10） |
| 任一阶段流程开销 > 产出时间 30% | 删掉贡献最小的那套方法论（D-009） |
| 非公开数据入库 | 立即停止，清理并复盘（D-010） |
